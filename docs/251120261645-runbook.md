### Step 1: SSH key (user, on the PC)

The key lets you log in to the VM. Oracle asks for the public half when the VM is created, so it comes first.

1. Press the Windows key, type `PowerShell`, open **Windows PowerShell**.
2. Paste and press Enter:

   ```powershell
   mkdir $HOME\.ssh -Force; ssh-keygen -t ed25519 -f $HOME\.ssh\oracle_mkc -C oracle-mkc-vm
   ```

3. `Enter passphrase`: press Enter (no passphrase) or type one you will remember. Then confirm.
4. It prints a fingerprint and some ASCII art: done.

**Check:** `C:\Users\<you>\.ssh\oracle_mkc` (private key, never shared, never committed) and `oracle_mkc.pub` (public key, one line starting with `ssh-ed25519`).

This key is for the admin login only. GitHub Actions gets its own deploy key (see "Deploy and rollback").

### Step 2: Create the VM (user, Oracle console)

1. Sign in at **cloud.oracle.com**.
2. Menu **☰** (top left) → **Compute → Instances** → **Create instance**.
3. **Name:** `mkc-k3s`.
4. **Placement:** leave the default.
5. **Image and shape:**
   - **Change image** → **Canonical Ubuntu**, version **24.04** (not "Minimal") → **Select image**.
   - **Change shape** → **Ampere** → **VM.Standard.A1.Flex** → 4 OCPUs, 24 GB ("Always Free-eligible") → **Select shape**.
6. **Networking:** keep "Create new virtual cloud network" and "Create new public subnet". "Automatically assign public IPv4 address" should be **on**.

9. **Create.** The status goes from Provisioning to **Running** in 1–3 minutes.

**If it says "Out of capacity for shape VM.Standard.A1.Flex"** (common for free ARM VMs): try another Availability domain under Placement, then 2 OCPUs / 12 GB.

### Step 5: Grow the VM to 4 OCPUs / 24 GB (user, Oracle console)

The Always Free allowance is 4 OCPUs and 24 GB in total, so this costs nothing. Do it before installing anything.

1. Open the instance **mkc-k3s**.
2. **Edit** (or **Actions / More actions → Edit**).
3. Section **Shape** → **Change shape** / **Edit shape**. The console moves this option around between versions: look for a pencil or Edit link next to "Shape" on the **Details** tab too. If the option is missing, **Stop** the instance first, then try again.

### Step 6: Open ports 80 and 443 in Oracle's network rules (user, Oracle console)

Two layers must both allow a port: Oracle's network rules (this step) and the VM's own firewall (step 7). Port 80 is needed for the Let's Encrypt check, 443 for HTTPS.

1. Instance **mkc-k3s** → tab **Networking** (or Attached VNICs).
2. Click the **Subnet** link.
3. Tab **Security** (or **Security Lists**) → **Default Security List for vcn-…**.
4. **Security rules** (or **Ingress Rules**) → **Add Ingress Rules**:
   - Source CIDR `0.0.0.0/0`, IP Protocol `TCP`, Destination Port Range `80`
   - **+ Another Ingress Rule**: the same with `443`
5. **Add Ingress Rules.**

**Never open port 6443** (the Kubernetes API). By design it stays closed to the internet (design doc section 10).

### Step 7: Open the VM's own firewall (agent, SSH)

Oracle's Ubuntu image rejects every incoming port except 22, and it rejects all forwarding, which breaks the k3s pod network.

```bash
sudo cp /etc/iptables/rules.v4 /etc/iptables/rules.v4.oracle-default   # backup
sudo iptables -I INPUT 5 -p tcp -m state --state NEW -m tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT 6 -p tcp -m state --state NEW -m tcp --dport 443 -j ACCEPT
# k3s pods and services must reach the node (for example the API server through 10.43.0.1).
# This does not expose 6443: internet traffic never comes from these ranges.
sudo iptables -I INPUT 7 -s 10.42.0.0/16 -j ACCEPT -m comment --comment "k3s pods"
sudo iptables -I INPUT 8 -s 10.43.0.0/16 -j ACCEPT -m comment --comment "k3s services"
sudo iptables -D FORWARD -j REJECT --reject-with icmp-host-prohibited
sudo netfilter-persistent save                                           # survives a reboot
```

The new rules go before the final `REJECT` line of INPUT; order matters.

**Check from outside** (nothing listens yet):

```bash
for p in 80 443 6443; do curl -s -o /dev/null --connect-timeout 8 http://92.6.240.17:$p; echo "port $p: curl exit $?"; done
```

- 80 and 443: exit 7 ("connection refused"): the packet reaches the VM, both layers let it through.
- 6443: exit 28 (timeout): Oracle blocks it, as intended.

### Step 9: Choose the API host name (user decision)

The API needs a host name that points at the VM, so Let's Encrypt can issue a certificate. Options offered:

| Option | Cost | Note |
|---|---|---|
| Own domain (e.g. `api.<name>.de`) | about €1–12 per year | professional; one DNS A record |
| DuckDNS subdomain | free | sign-up; less professional |
| **sslip.io** | free | **chosen** (decision 43): no sign-up, no DNS record |
| An existing domain | — | one A record |

sslip.io answers every name `a-b-c-d.sslip.io` with the IP `a.b.c.d`, so `92-6-240-17.sslip.io` points at the VM already.

**Check:** `nslookup 92-6-240-17.sslip.io` gives `92.6.240.17`; `curl http://92-6-240-17.sslip.io/` gives Traefik's 404.

**Limits:** the name is tied to the IP (a new IP means a new name: update the Helm values, `VITE_API_URL` in Vercel and the CORS settings); Let's Encrypt rate limits may be shared with other sslip.io users. Moving to an own domain later is a value change.

## Deploy and rollback (first deploy and drill done 25.11.2026, MKC-10)

A merge to `main` deploys by itself: the backend to k3s, then the frontend to Vercel. Each job that uses the `production` environment waits for its own approval: once for `backend`, once for `frontend`. Since decision 51 the development agent approves both after a PASS merge with green CI; with parallel lanes (decision 61) the coordinator does it:

```bash
RUN=<cd run id>; ENV_ID=$(gh api repos/qamran/Messkonzept-Copilot/environments/production --jq .id)
gh api -X POST repos/qamran/Messkonzept-Copilot/actions/runs/$RUN/pending_deployments \n  -F "environment_ids[]=$ENV_ID" -f state=approved -f comment="PASS merge, CI green"
```

Run it once when `backend` waits and again when `frontend` waits. The user can reject a waiting deploy in the run's page at any time. This section explains the path, the one-time VM setup, the rollback drill and what to do by hand.

### How a deploy runs

`.github/workflows/cd.yml`, on every push to `main` in `qamran/Messkonzept-Copilot` (never on the Turing mirror):

1. **Job `image`** (no secrets): waits up to 40 minutes until the CI job `publish` has pushed `ghcr.io/qamran/messkonzept-copilot-backend:<commit>` with an arm64 image. It never falls back to `:main`.
2. **Job `backend`** (environment `production`, waits for **Approve**):
   - checks that port 6443 times out from the runner (the Kubernetes API stays closed)
   - runs `scripts/cd_deploy.sh <commit>`:
     - SSH to `mkc-deploy@92.6.240.17` with the deploy key and the pinned host key; the request is `deploy <commit>`
     - on the VM the forced command `mkc-deploy` first asks GitHub's compare API whether the commit is on `main` (GitHub also serves a fork's commits under our URL; anything else is refused with exit 4), then downloads the chart at that commit from GitHub and runs `helm upgrade --install --rollback-on-failure --wait=watcher --timeout 600s` with `/etc/mkc/values.yaml`
     - smoke test over real HTTPS: `/health` answers and `/api/version` reports the commit (30 tries, 10 s apart)
     - on a failed smoke test: SSH `rollback` (Helm goes back one revision) and the job fails
3. **Job `frontend`** (environment `production`, after `backend`): `vercel pull`, `vercel build --prod` with `VITE_COMMIT=<commit>`, `vercel deploy --prebuilt --prod`; then `/` and `/admin` must answer.

Vercel's own Git integration builds previews for PRs, but never `main` (`frontend/vercel.json`), so production only changes after the backend is live.

### Who may do what

| Who | Can | Can't |
|---|---|---|
| GitHub Actions (deploy key) | `deploy <40-hex commit>`, `rollback`, `status` | a shell, other commands, port forwarding, files (`restrict`, forced command) |
| `mkc-deploy` on the VM | Helm and kubectl in namespace `mkc` (ServiceAccount `mkc-deployer`, role `admin`) | other namespaces, cluster resources, `sudo` |
| Admin (`ubuntu`, key `~/.ssh/oracle_mkc`) | everything | — |

### One-time VM setup (done 25.11.2026)

Files from the repo: `deploy/vm/mkc-deploy`, `deploy/vm/rbac.yaml`, `deploy/vm/values-production.yaml`.

1. **Helm on the VM** (agent, SSH):

   ```bash
   curl -fsSLO https://get.helm.sh/helm-v4.3.1-linux-arm64.tar.gz
   curl -fsSLO https://get.helm.sh/helm-v4.3.1-linux-arm64.tar.gz.sha256sum
   sha256sum -c helm-v4.3.1-linux-arm64.tar.gz.sha256sum   # 8cf8f66e…4f88: OK
   ```

2. **Namespace and rights:** `sudo k3s kubectl apply -f rbac.yaml` (namespace `mkc` with Pod Security `restricted`, ServiceAccount `mkc-deployer`, RoleBinding to `admin` in `mkc` only, a token Secret). Before adding the Pod Security label to a namespace with pods, `kubectl label --dry-run=server` shows any pod that would break it (none here).
3. **User:** `sudo useradd --create-home --shell /bin/bash mkc-deploy`, then `sudo usermod -p '*' mkc-deploy` (no password; key login only). No sudo rights.
4. **Files:** `/etc/mkc/values.yaml` (from `values-production.yaml`) and `/usr/local/bin/mkc-deploy`, both owned by root (`0644` and `0755`).
5. **Kubeconfig** for `mkc-deploy` in `/home/mkc-deploy/.kube/config` (`0600`): server `https://127.0.0.1:6443`, the cluster CA, the token from Secret `mkc-deployer-token`. Built on the VM without printing the token.
6. **Check the rights** (`sudo -u mkc-deploy -H k3s kubectl --kubeconfig /home/mkc-deploy/.kube/config auth can-i …`): create deployments, secrets and ingresses in `mkc`: yes. Secrets in `kube-system`, deployments in `default`, nodes, clusterrolebindings, clusterissuers: no.
7. **Database secret** (agent, from the gitignored `backend/.env`, over stdin so the value is never in a command line or log):

   ```bash
   grep '^DATABASE_URL=' backend/.env | tr -d '\r' | ssh -i ~/.ssh/oracle_mkc ubuntu@92.6.240.17 \
     'sudo k3s kubectl -n mkc create secret generic mkc-secrets --from-env-file=/dev/stdin --dry-run=client -o yaml | sudo k3s kubectl apply -f -'
   ```

8. **Deploy key:** an ed25519 key made for GitHub Actions only. Its public half goes into `/home/mkc-deploy/.ssh/authorized_keys` (root-owned, `0644`) as:

   ```text
   restrict,command="/usr/local/bin/mkc-deploy" ssh-ed25519 AAAA… mkc-deploy-github-actions
   ```

   The private half goes into the `production` environment as the secret `DEPLOY_SSH_KEY` (user, see below) and is then deleted from the PC.
9. **Negative checks** with the deploy key (25.11.2026): an empty command, `id`, `bash -i`, `deploy abc`, `deploy 1f16ba8`, `status; id` and `cat …/.kube/config` are refused (exit 2); a PTY is refused; sftp closes; `-L 16443:127.0.0.1:6443` gives "administratively prohibited". ### Roll back by hand

- **To the previous revision:** with the deploy key, `ssh mkc-deploy@92.6.240.17 rollback`. As admin: `sudo -u mkc-deploy -H helm rollback mkc -n mkc --wait=watcher --timeout 600s`.
- **To a given revision:** as admin, `sudo -u mkc-deploy -H helm history mkc -n mkc`, then `sudo -u mkc-deploy -H helm rollback mkc <revision> -n mkc --wait=watcher --timeout 600s`.
- **To an older commit:** `scripts/cd_deploy.sh <commit>` with the deploy key. The commit must have an image in GHCR (every merge to `main` does).
- **Frontend:** in Vercel, **Deployments** → an older production deployment → **⋯** → **Promote to Production** (or `vercel rollback`). Then the page may show the API-version warning until both sides match again.

### Change a setting or a secret

- **Non-secret setting** (host, CORS, Clerk issuer): edit `deploy/vm/values-production.yaml` in a PR. After the merge, copy it to the VM as admin: `scp … ubuntu@92.6.240.17:/tmp/values.yaml`, then `sudo install -o root -g root -m 0644 /tmp/values.yaml /etc/mkc/values.yaml`. The next deploy uses it.
- **Secret** (`DATABASE_URL`): run step 7 again. Pods don't restart by themselves when an existing Secret changes, so restart them as admin: `sudo k3s kubectl -n mkc rollout restart deploy/mkc-api deploy/mkc-worker`.
- **New IP address:** a new sslip.io name. Change `ingress.host` in the values, Vercel's `VITE_API_URL`, `API_URL` and the pinned host key in `cd.yml`, and the default host in `scripts/cd_deploy.sh`.

### Database migrations

From MKC-11 (decision 48) every deploy migrates first:

- The Helm hook Job `mkc-migrate` runs `alembic upgrade head` before any pod changes. It is kept after it ran, so its log can be read: `sudo k3s kubectl -n mkc logs job/mkc-migrate`.
- If it fails, the Helm upgrade fails and `--rollback-on-failure` keeps the old release. The smoke test never runs, and `cd.yml` reports the failed deploy.
- **Additive only:** a migration may add tables and columns, never drop or rename them in the same release. `helm rollback` does not undo a migration, so the previous release must keep working on the new schema. Remove old columns in a later release.

## Backups and restore drill (first backup and drill done 26.11.2026, MKC-11)

A nightly CronJob backs up the database to Oracle Object Storage (decision 49). The first production backup and the first restore drill were done on 26.11.2026; the results are at the end of this section.

### How a backup runs

1. 03:30 Europe/Berlin: the CronJob `mkc-backup` starts one pod (never two at once).
2. It writes a row `running` to `backup_runs`.
3. `pg_dump --schema=public --no-owner --no-privileges` (pg_dump 17) → gzip → a size-limited work volume.
4. PUT to the upload link + `nightly/mkc-<UTC time>.sql.gz`.
5. The row becomes `ok` (object name, size) or `failed` (a short error, never the link or the password). The log has one line per run.

Check it: `GET /api/admin/backup-status` (admin token): `state`, `last_run`, `last_success`, `stale` (no good backup in 26 h). As admin on the VM: `sudo k3s kubectl -n mkc get cronjob,jobs` and `sudo k3s kubectl -n mkc logs job/<name>`.

## Worker lease and outages

How the worker holds a run, what happens on a deploy or crash, and what it does when the database is gone (MKC-17, decision 57). Every timing is a setting with a default; change it like any other setting (section "Change a setting or a secret").

### Timings

| Setting | Default | What it does |
|---|---|---|
| `MKC_WORKER_POLL_SECONDS` | 1 | Wait between polls when there is no run; also how often the heartbeat file is touched |
| `MKC_WORKER_HEARTBEAT_FILE` | empty (the chart sets `/tmp/mkc-worker-heartbeat`) | File the heartbeat thread touches; the probe `mkc-worker-health` reads it |
| `MKC_WORKER_HEARTBEAT_MAX_AGE_SECONDS` | 30 | The probe fails when the file is older |
| `MKC_WORKER_LEASE_SECONDS` | 120 | How long a claimed run stays leased without a renewal; a crashed worker's run is taken over after at most this long |
| `MKC_WORKER_LEASE_RENEW_SECONDS` | 20 | How often the lease thread renews the lease (a thread of its own, next to the heartbeat thread); three renewals must fit into one lease, or the worker refuses to start |
| `MKC_WORKER_DB_BACKOFF_MAX_SECONDS` | 30 | Longest wait between database probes during an outage (1, 2, 4 … 30 s); also the pause after an unexpected error (a setup error stops the run instead, section "Limits and retries") |
| `MKC_DATABASE_CONNECT_TIMEOUT_SECONDS` | 10 | A connection attempt fails after this long (plus TCP keepalives), so a paused database does not hang the worker |

### What happens when

- **Deploy (`helm upgrade`) or pod delete:** SIGTERM. The worker finishes the current turn, stores it, releases the lease and exits (log: `signal SIGTERM received, stopping`, then `worker stopped`). The new pod claims the run at once and resumes at the next turn. The grace period is 300 s; a turn that runs longer is killed and handled like a crash.
- **Crash or kill:** the lease runs out after at most `MKC_WORKER_LEASE_SECONDS`. The next worker claims the run and resumes from the last complete turn; the turn that was in flight is asked again.
- **Database unreachable:** the worker logs `database unavailable (…), waiting`, probes with backoff and keeps its heartbeat file fresh, so Kubernetes does not restart it. When the database is back it logs `database available again`, sets the run to `waiting_for_database`, then claims it back to `running` and resumes. Nothing that was stored is lost. SIGTERM during an outage still stops the worker; the lease then runs out on its own.
- **Lease taken over** (only if two workers ever ran at once): the worker that lost the lease cannot store anything more (log: `lease lost`); the other one carries on.

### Look at the lease

Read-only, from a machine that can reach the database:

```sql
select id, state, lease_owner, lease_expires_at, now() from run order by id desc limit 5;
```

`lease_owner` is `<pod name>-<pid>-<random>`. An empty owner means the run is free. A run whose `lease_expires_at` is in the past is free to the next claim.

## Limits and retries

What stops a run or an item, and how model calls are retried (MKC-18, decision 58; the reasons for each default are in the plan `docs/superpowers/plans/271120261324-mkc-18-limits-retries.md`). Every limit is a setting; change it like any other setting (section "Change a setting or a secret").

### Settings

| Setting | Default | What it does |
|---|---|---|
| `MKC_ITEM_MAX_STEPS` | 12 | Model calls one item may make; then the item fails with `step_limit` |
| `MKC_RUN_MAX_STEPS` | 300 | Stored turns of all items of one run; then the run stops with `run_step_limit` |
| `MKC_RUN_MAX_WALL_SECONDS` | 7200 | Seconds since the run started (database clock, outages included); then the run stops with `wall_time` |
| `MKC_RUN_MAX_COST_EUR` | 3.00 | EUR the run's stored turns may cost; then the run stops with `cost_limit` (one call can go over) |
| `MKC_TOOL_MAX_RETRIES` | 3 | Failed calls of one tool in one item that the model may retry; one more fails the item with `tool_retries: <tool>` |
| `MKC_MODEL_MAX_RETRIES` | 4 | Retries of a model call after a 429, 5xx, timeout or network error; then the run stops with `model_unavailable` |
| `MKC_MODEL_BACKOFF_BASE_SECONDS` | 2 | First wait before a retry; it doubles per retry (2, 4, 8, 16 s), or the provider's `Retry-After` if longer |
| `MKC_MODEL_BACKOFF_MAX_SECONDS` | 60 | Longest wait between two attempts |
| `MKC_TURN_TIMEOUT_SECONDS` | 180 | Wall-clock deadline of one model call; after it the call counts as a timeout and is retried |
| `MKC_ITEM_MAX_RESUMES` | 3 | Resumes of an item without a new stored turn (crash loops); one more fails it with `resume_limit` |

One more rule has no setting: a reply without a tool call gets one corrective re-prompt; a second one fails the item with `malformed_output`.

### What a stop looks like

- **A run stop** (`run_step_limit`, `wall_time`, `cost_limit`, `setup_error`, `model_unavailable`): the run is `stopped` and `run.stop_reason` says why. Its items stay as they were: the item in flight keeps its checkpoint, queued items stay queued. The worker logs `run <id> stopped: <reason>`. A stopped run is not claimed again (resuming it is a later ticket).
- **An item failure** (`step_limit`, `tool_retries`, `malformed_output`, `resume_limit`, `model_error: <class>`, `tool_error: <class>`): the item is `failed`, `item.failure_reason` says why, the run goes on with the next item. The worker logs `item <id> failed: <reason>`.
- **`setup_error`:** a missing key or setting, a replay miss, a key the provider refused (401) or no credits left (402). Fix the setting, secret or credits, then start a new run. A 403 (on OpenRouter possibly a moderation flag on one input) fails only that item.
- **`model_unavailable`:** the provider kept failing for about 30 s of retries. Check the provider's status page, then start a new run.
- **SIGTERM during a retry wait:** the wait ends at once; the item stays `running` and the next worker resumes it.
- **What counts as a resume without progress:** every resume before the item's next stored turn. A deploy after a stored turn is reset by the next turn, so deploys never add up; a SIGTERM during a backoff or an outage before the item's first turn does count.
- **Known limits:** a model call that raises writes no turn and its `CallTrace` has no usage, so its cost is recorded nowhere (only a call cut off by the turn deadline that later returns is traced with its usage); a call cut off by the turn deadline may still finish and bill in the background.

### Look at the stops

Read-only, from a machine that can reach the database:

```sql
select id, state, stop_reason, started_at, now() - started_at as wall from run order by id desc limit 5;
select id, run_id, state, failure_reason, attempts_without_progress from item where state = 'failed' order by id desc limit 10;
```

## Tracing

Every model call attempt, tool call, stop and database outage of a run is one row in the table `run_log` and one observation in Langfuse (MKC-19, decision 59). One run is one Langfuse trace; its id is `run.trace_id`.

### Tracing settings

| Setting | Default | What it does |
|---|---|---|
| `MKC_LANGFUSE_PUBLIC_KEY` | empty | Langfuse project key (`pk-lf-...`). Empty: no Langfuse, `run_log` still records everything |
| `MKC_LANGFUSE_SECRET_KEY` | empty | Langfuse secret key (`sk-lf-...`); a secret, in `mkc-secrets` in production |
| `MKC_LANGFUSE_BASE_URL` | `https://cloud.langfuse.com` | the Langfuse host of the project's region |
| `MKC_LANGFUSE_ENVIRONMENT` | `development` | the trace's environment; `production` on the VM, so local runs never mix with production in one project |
| `MKC_LANGFUSE_TIMEOUT_SECONDS` | 5 | timeout of one export; bounds the flush after each run and on shutdown |

### What is sent

- **Model calls:** generations with the model id, tokens, latency, error and cost. Langfuse counts USD, so the EUR cost goes back to USD at the rate in `models.yaml`. Replayed calls send no cost.
- **Tool calls:** tool observations with the tool name (cut to 100 characters), ok or error code, refused, cached, latency.
- **Stops and outages:** events with the reason.
- **Errors (since MKC-20):** Langfuse gets only the error class and an HTTP status (`TransientModelError (HTTP 429)`), a tool error code, or a tool name cut to 100 characters, as `status_message`. The error text can quote a prompt or a model reply, so it stays in `run_log.error` (cut to 500 characters). Without a trace id (`run.trace_id` not set) nothing goes to Langfuse; `run_log` still records.
- **Never sent:** prompts, model replies, tool arguments, PDF text. Langfuse keeps what it gets, and the model route has zero data retention. The SDK becomes the process's OpenTelemetry provider; only its own observations are exported (`is_langfuse_span`), so other libraries' spans (the Anthropic SDK traces its calls with the prompt) never leave.
- **Failure safety:** a Langfuse or `run_log` failure is logged (`not sent to the trace sink`, `not written to run_log`) and the run goes on. An unreachable Langfuse costs at most the export timeout per flush.
- **Known limits:** a failed model call has no tokens and no cost (the provider reports none); a span's start in Langfuse is late by the call's latency (its duration is right).

## Baseline, faults and the CLI

MKC-20 (decision 60) adds a second harness mode for E4, failure injection and a command line for runs.

### Harness mode

| Setting | Default | What it does |
|---|---|---|
| `MKC_HARNESS_MODE` | `full` | mode of new runs: `full`, or `baseline` (the simple loop). Each run keeps the mode it was created with (`run.mode`); the worker runs every run in its own mode |

Baseline is the same loop, tools, prompts, limits, retries and tracing as full, with five switches off:

| Switch | Full | Baseline |
|---|---|---|
| `checkpoints` | a `turn` row per turn; an interrupted item resumes at its last complete turn | no turn rows; every attempt starts from the item task |
| `tool_cache` | `tool_cache` lookups and writes | none |
| `durable_queue` | claims and item end states are written as they happen | they stay in memory and are written once, when the run settles or stops; a crash or SIGTERM before that writes nothing, so the next attempt starts from zero |
| `idempotency` | `save_draft` keyed by (document hash, concept key) | no key: a second save is a second entry |
| `durable_approvals` | drafts in the `draft` table | drafts in memory only; they die with the process |

The switches go in pairs where the loop needs it: `checkpoints` with `durable_queue`, `idempotency` with `durable_approvals`; only `tool_cache` can be off alone. `Switches` refuses other mixes.

Baseline still writes the run and item rows that define the work, the lease, the end report and `run_log`. Its run limits count turns and cost in memory, and wall time from the start of the attempt.

**Known limit:** each baseline attempt starts its limits from zero. A baseline run that crashes again and again in the worker is claimed again after each lease expiry and has no cap across attempts. Run baseline runs with `--inline` (E4 does), not through the worker.

### The run CLI

The command is `mkc` (`cd backend && uv run mkc ...`; in the image, `mkc ...`). It uses `DATABASE_URL` and the model settings like the worker.

- `mkc run start --items FILE [--mode full|baseline] [--inline] [--faults FILE --plan NAME]`: creates a run and one `queued` item per entry of the items file. Until MKC-21, the file is a synthetic YAML list of `concept_key`, `document_hash` and `task` (a mapping the model is told). Without `--inline` the worker picks the run up. With `--inline` the CLI claims that run with its own lease (`cli-<host>-<pid>-<random>`) and runs it in the process; a worker can't take it meanwhile.
- `mkc run resume RUN_ID [--inline] [--faults FILE --plan NAME]`: a `stopped` run goes back to `running`. The stop reason and the wall clock are cleared; in full mode, steps and cost keep counting from the stored turns, so a run stopped on `cost_limit` stops again at once (raise `MKC_RUN_MAX_COST_EUR` first). A baseline run runs its open items again from their tasks; items that ended before the stop keep their state, so a baseline item can be `draft_saved` with no `draft` row (its draft was in memory). A `running` or `waiting_for_database` run is left as it is; `done` and `awaiting_approval` are refused.
- `mkc run status RUN_ID`: state, mode, stop reason, items per state, usage (steps, cost, wall time) and lease. A baseline run has no turn rows, so its usage is the model calls and cost in `run_log`, over all attempts.
- `mkc run inspect RUN_ID [--item ID]`: one line per item (state, failure reason, turns, cost) and the latest 20 `run_log` rows; with `--item`, that item's turns (tool names and ok or failed, never content).

Exit codes: 0 done, 1 refused (no such run, wrong state, leased by a worker), 2 bad input (items file, fault file, plan name), 137 killed by a fault plan.

Example (local database, replayed or fake model):

```bash
cd backend
uv run mkc run start --items /path/to/items.yaml --mode baseline --inline
uv run mkc run status 1
uv run mkc run inspect 1 --item 1
```

**Recovery of a stopped run** (MKC-18 finding 2): read the reason with `mkc run status`, fix its cause (a key, credits, a limit setting, the provider), then `mkc run resume RUN_ID`. The worker continues the run; the item in flight resumes at its last complete turn.

### Fault plans (E4)

A fault plan says where faults happen. Each field is a 1-based count, or empty for no such fault. Each fault fires at most once per process.

| Field | Fault |
|---|---|
| `timeout_at` | the n-th tool call times out: `ok: false`, code `timeout`, the tool does not run; it counts as a tool failure |
| `rate_limit_at` | the n-th model call attempt gets a 429 before it reaches the provider; the harness backs off and retries |
| `malformed_at` | the n-th model call attempt returns a reply with no tool call, at no cost; the harness sends its one re-prompt |
| `kill_at_turn` | the n-th model call attempt reaches the provider, then the process dies before its results are stored |
| `kill_during_approval` | the process dies right after the n-th item ends `draft_saved` (until MKC-23, a saved draft is the pending approval) |

- `backend/data/e4_faults.yaml` holds one plan per fault type plus `no_faults`; `mkc.harness.faults.load_fault_plans` reads it and refuses unknown keys and counts below 1.
- A plan comes only from `--faults FILE --plan NAME` or a test, never from a setting, so a production worker can't inject faults.
- An injected kill in the CLI releases the lease and exits 137; `mkc run resume RUN_ID --inline` continues at once (a real kill leaves the lease to expire, 120 s).
- An injected 429, malformed reply or tool timeout never reaches the provider or the registry, so it has no `run_log` row; count it from the fault plan, the backoff, the re-prompt turn or the tool's failed result.
- **Replay (for MKC-32):** a re-prompt, a faulted tool result or a resume context changes the next request, so its replay key differs from a no-fault recording. Record each fault arm once (`MKC_MODEL_MODE=record`) before replaying it; a missing recording stops the run with `setup_error`.
