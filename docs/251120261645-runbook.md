# Runbook

How to set up, deploy, roll back and restore Messkonzept-Copilot. Each section says when it was last done for real.

## Server setup (done 25.11.2026, MKC-10)

The backend runs on one Oracle Cloud Always Free VM with k3s (ADR 002, decisions 43 and 44). The frontend runs on Vercel. This section is the exact path taken on 25.11.2026, one step at a time, with the check after each step and the problems met on the way. No secret values are written here.

**Who does what:**

- **User:** steps in a web console (Oracle, GitHub, Vercel) and anything that creates a key or a token.
- **Agent:** steps over SSH on the VM and with the `gh` and `vercel` CLIs.

**Result at the end:**

| Part | State |
|---|---|
| Oracle VM `mkc-k3s` | 4 OCPUs, 24 GB, Ubuntu 24.04 arm64, public IP `92.6.240.17` |
| Firewalls | 80 and 443 open; 6443 (Kubernetes API) closed from outside |
| k3s | v1.37.2+k3s1 with Traefik |
| cert-manager | v1.21.3, ClusterIssuers `letsencrypt-staging` and `letsencrypt-prod` |
| API host name | `92-6-240-17.sslip.io` |
| Vercel | project `messkonzept-copilot`, preview per PR |
| GitHub | environment `production` with a required reviewer and the secret `VERCEL_TOKEN` |

### Step 1: SSH key (user, on the PC)

The key lets you log in to the VM. Oracle asks for the public half when the VM is created, so it comes first.

1. Press the Windows key, type `PowerShell`, open **Windows PowerShell**.
2. Paste and press Enter:

   ```powershell
   mkdir $HOME\.ssh -Force; ssh-keygen -t ed25519 -f $HOME\.ssh\oracle_mkc -C oracle-mkc-vm
   ```

3. `Enter passphrase`: press Enter (no passphrase) or type one you will remember. Then confirm.
4. It prints a fingerprint and some ASCII art: done.

**Check:** `C:\Users\<you>\.ssh\oracle_mkc` (private key, never shared, never committed) and `oracle_mkc.pub` (public key, one line starting with `ssh-ed25519`).

This key is for the admin login only. GitHub Actions gets its own deploy key (see "Deploy and rollback").

### Step 2: Create the VM (user, Oracle console)

1. Sign in at **cloud.oracle.com**.
2. Menu **☰** (top left) → **Compute → Instances** → **Create instance**.
3. **Name:** `mkc-k3s`.
4. **Placement:** leave the default.
5. **Image and shape:**
   - **Change image** → **Canonical Ubuntu**, version **24.04** (not "Minimal") → **Select image**.
   - **Change shape** → **Ampere** → **VM.Standard.A1.Flex** → 4 OCPUs, 24 GB ("Always Free-eligible") → **Select shape**.
6. **Networking:** keep "Create new virtual cloud network" and "Create new public subnet". "Automatically assign public IPv4 address" should be **on**.
7. **Add SSH keys:** **Paste public keys** → paste the whole line from `oracle_mkc.pub`.
8. **Boot volume:** leave the defaults.
9. **Create.** The status goes from Provisioning to **Running** in 1–3 minutes.

**If it says "Out of capacity for shape VM.Standard.A1.Flex"** (common for free ARM VMs): try another Availability domain under Placement, then 2 OCPUs / 12 GB.

**What happened on 25.11.2026:** the VM came up in AD-2 with **1 OCPU, 6 GB and no public IP** (Public IP column "–"). Steps 3 and 4 fix both.

### Step 3: Give the VM a public IP (user, Oracle console)

Without a public IP the VM can't be reached.

1. Click the instance **mkc-k3s**.
2. Tab **Networking** (older layout: Resources → **Attached VNICs**).
3. Click the VNIC (usually named `mkc-k3s`, marked Primary).
4. Tab **IP administration** (or **IPv4 addresses**).
5. Row with the private IP (here `10.0.0.102`) → **⋯** → **Edit**.
6. **Public IP type:** **Ephemeral public IP** → **Update**.

If "Ephemeral public IP" is greyed out, the subnet is private; fix the subnet first.

**Check:** the public IP shows in the row and in the instance list. Here: `92.6.240.17`. An ephemeral IP survives stop and start; it is lost only if the VM is terminated.

### Step 4: Test the login (agent, SSH)

```bash
ssh -i ~/.ssh/oracle_mkc -o StrictHostKeyChecking=accept-new ubuntu@92.6.240.17 \
  "uname -m; grep PRETTY_NAME /etc/os-release; nproc; free -h | head -2; df -h / | tail -1; sudo iptables -S INPUT"
```

- The user name is `ubuntu` on Ubuntu images (`opc` on Oracle Linux).
- `accept-new` stores the VM's host key on the first login.

**Check (25.11.2026):** `aarch64`, Ubuntu 24.04.5 LTS, 1 CPU, 5.8 GiB, 45 GB disk, no k3s, firewall allows only port 22.

### Step 5: Grow the VM to 4 OCPUs / 24 GB (user, Oracle console)

The Always Free allowance is 4 OCPUs and 24 GB in total, so this costs nothing. Do it before installing anything.

1. Open the instance **mkc-k3s**.
2. **Edit** (or **Actions / More actions → Edit**).
3. Section **Shape** → **Change shape** / **Edit shape**. The console moves this option around between versions: look for a pencil or Edit link next to "Shape" on the **Details** tab too. If the option is missing, **Stop** the instance first, then try again.
4. Keep **VM.Standard.A1.Flex**; set **4 OCPUs** and **24 GB** → **Save changes**.
5. The instance restarts by itself (no need to stop it first). Wait until it shows **Running** again; SSH fails while it reboots.

If it says "Out of capacity", try 2 OCPUs / 12 GB, or stay at 1/6 for a start.

**Check:** `ssh … "nproc; free -h"` gives 4 and 23 GiB. The public IP stays the same.

### Step 6: Open ports 80 and 443 in Oracle's network rules (user, Oracle console)

Two layers must both allow a port: Oracle's network rules (this step) and the VM's own firewall (step 7). Port 80 is needed for the Let's Encrypt check, 443 for HTTPS.

1. Instance **mkc-k3s** → tab **Networking** (or Attached VNICs).
2. Click the **Subnet** link.
3. Tab **Security** (or **Security Lists**) → **Default Security List for vcn-…**.
4. **Security rules** (or **Ingress Rules**) → **Add Ingress Rules**:
   - Source CIDR `0.0.0.0/0`, IP Protocol `TCP`, Destination Port Range `80`
   - **+ Another Ingress Rule**: the same with `443`
5. **Add Ingress Rules.**

**Never open port 6443** (the Kubernetes API). By design it stays closed to the internet (design doc section 10).

### Step 7: Open the VM's own firewall (agent, SSH)

Oracle's Ubuntu image rejects every incoming port except 22, and it rejects all forwarding, which breaks the k3s pod network.

```bash
sudo cp /etc/iptables/rules.v4 /etc/iptables/rules.v4.oracle-default   # backup
sudo iptables -I INPUT 5 -p tcp -m state --state NEW -m tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT 6 -p tcp -m state --state NEW -m tcp --dport 443 -j ACCEPT
# k3s pods and services must reach the node (for example the API server through 10.43.0.1).
# This does not expose 6443: internet traffic never comes from these ranges.
sudo iptables -I INPUT 7 -s 10.42.0.0/16 -j ACCEPT -m comment --comment "k3s pods"
sudo iptables -I INPUT 8 -s 10.43.0.0/16 -j ACCEPT -m comment --comment "k3s services"
sudo iptables -D FORWARD -j REJECT --reject-with icmp-host-prohibited
sudo netfilter-persistent save                                           # survives a reboot
```

The new rules go before the final `REJECT` line of INPUT; order matters.

**Check from outside** (nothing listens yet):

```bash
for p in 80 443 6443; do curl -s -o /dev/null --connect-timeout 8 http://92.6.240.17:$p; echo "port $p: curl exit $?"; done
```

- 80 and 443: exit 7 ("connection refused"): the packet reaches the VM, both layers let it through.
- 6443: exit 28 (timeout): Oracle blocks it, as intended.

### Step 8: Install k3s (agent, SSH)

```bash
curl -sfL https://get.k3s.io -o /tmp/k3s-install.sh
sudo INSTALL_K3S_VERSION="v1.37.2+k3s1" sh /tmp/k3s-install.sh
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl -n kube-system rollout status deploy/traefik --timeout=180s
```

- The version is pinned: v1.37.2+k3s1 was the stable channel on 25.11.2026 and older than two weeks (check the channel with `curl -sI https://update.k3s.io/v1-release/channels/stable`).
- k3s ships **Traefik** as the Ingress controller (the chart's default `ingress.className`). Its LoadBalancer listens on the VM's ports 80 and 443.

**Check:** node `mkc-k3s` Ready, v1.37.2+k3s1, arm64; from outside, `curl http://92.6.240.17/` gives **HTTP 404** from Traefik (no app yet).

### Step 9: Choose the API host name (user decision)

The API needs a host name that points at the VM, so Let's Encrypt can issue a certificate. Options offered:

| Option | Cost | Note |
|---|---|---|
| Own domain (e.g. `api.<name>.de`) | about €1–12 per year | professional; one DNS A record |
| DuckDNS subdomain | free | sign-up; less professional |
| **sslip.io** | free | **chosen** (decision 43): no sign-up, no DNS record |
| An existing domain | — | one A record |

sslip.io answers every name `a-b-c-d.sslip.io` with the IP `a.b.c.d`, so `92-6-240-17.sslip.io` points at the VM already.

**Check:** `nslookup 92-6-240-17.sslip.io` gives `92.6.240.17`; `curl http://92-6-240-17.sslip.io/` gives Traefik's 404.

**Limits:** the name is tied to the IP (a new IP means a new name: update the Helm values, `VITE_API_URL` in Vercel and the CORS settings); Let's Encrypt rate limits may be shared with other sslip.io users. Moving to an own domain later is a value change.

### Step 10: Install cert-manager and the Let's Encrypt issuers (agent, SSH)

```bash
sudo k3s kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.21.3/cert-manager.yaml
for d in cert-manager cert-manager-webhook cert-manager-cainjector; do
  sudo k3s kubectl -n cert-manager rollout status deploy/$d --timeout=180s
done
```

v1.21.3 (23.10.2026) was the newest stable release older than two weeks.

Two ClusterIssuers, HTTP-01 through Traefik. The e-mail address is optional for Let's Encrypt and left out, so no personal data is sent.

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-staging
spec:
  acme:
    server: https://acme-staging-v02.api.letsencrypt.org/directory
    privateKeySecretRef:
      name: letsencrypt-staging-account
    solvers:
      - http01:
          ingress:
            ingressClassName: traefik
---
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    privateKeySecretRef:
      name: letsencrypt-prod-account
    solvers:
      - http01:
          ingress:
            ingressClassName: traefik
```

**Check:** a test `Certificate` for `92-6-240-17.sslip.io` from `letsencrypt-staging` (generous rate limits) was Ready after 35 s. That proves the whole path: DNS → Oracle → VM firewall → Traefik → cert-manager → Let's Encrypt. The test certificate and its secret were deleted afterwards.

### Step 11: Vercel project (user + agent)

The user already had a Vercel account (Hobby plan, scope `qamran`), and the `vercel` CLI was logged in on the PC (`vercel whoami --format json`).

1. **Agent:** create the project with the API. On Git Bash, set `MSYS_NO_PATHCONV=1`, or Git Bash turns `/v11/projects` into a Windows path ("Invalid arguments").

   ```bash
   MSYS_NO_PATHCONV=1 vercel api /v11/projects -X POST --scope qamran --input project.json
   ```

   with `project.json`:

   ```json
   {"name": "messkonzept-copilot", "framework": "vite", "rootDirectory": "frontend",
    "buildCommand": "npm run build", "outputDirectory": "dist", "installCommand": "npm ci",
    "gitRepository": {"type": "github", "repo": "qamran/Messkonzept-Copilot"}}
   ```

2. **First try failed:** "To link a GitHub repository, you need to install the GitHub integration first." Vercel's GitHub App had no access to this repo.
3. **User:** open <https://github.com/settings/installations> → **Vercel** → **Configure** → Repository access: **Only select repositories** → **Select repositories** → add `qamran/Messkonzept-Copilot` → **Save** (GitHub may ask for the password or 2FA).
4. **Agent:** the same API call again: project created, linked to the repo, production branch `main`.
5. **Agent:** Node 24 (as in CI; Vercel defaulted to 26):

   ```bash
   MSYS_NO_PATHCONV=1 vercel api /v9/projects/messkonzept-copilot -X PATCH -f nodeVersion=24.x --scope qamran
   ```

6. **Agent:** environment variables for production and preview, read from `frontend/.env.local` without printing them:
   - `VITE_CLERK_PUBLISHABLE_KEY`: the Clerk development instance's `pk_test_` key (a publishable key, not a secret; decision 39)
   - `VITE_API_URL=https://92-6-240-17.sslip.io`

   ```bash
   printf '%s' "$VALUE" | vercel env add VITE_API_URL production --project messkonzept-copilot --scope qamran --non-interactive
   ```

**Check:** `MSYS_NO_PATHCONV=1 vercel api /v10/projects/messkonzept-copilot/env --scope qamran` lists both names for `production` and `preview`.

**Still in the repo (MKC-10):** `frontend/vercel.json` turns off Vercel's own production deploys from `main` (the deploy workflow deploys the backend first, then the frontend) and adds the page fallback for `/admin`.

### Step 12: GitHub `production` environment (agent)

```bash
UID_=$(gh api users/qamran --jq .id)
printf '{"reviewers":[{"type":"User","id":%s}],"prevent_self_review":false,"deployment_branch_policy":{"protected_branches":true,"custom_branch_policies":false}}' "$UID_" \
  | gh api -X PUT repos/qamran/Messkonzept-Copilot/environments/production --input -
```

- Required reviewer `qamran`: every deploy waits for the user's **Approve** click.
- Deployment branches: protected branches only, which means `main`.

### Step 13: Vercel token (user)

The deploy workflow needs a token to deploy the frontend. Never paste it into a chat or a file.

1. Open <https://vercel.com/account/settings/tokens>.
2. **Name** `mkc-github-cd`, **Scope** your account (`Qamran`), **Expiration** 1 year (or 90 days to rotate more often) → **Create** → copy the token (shown once).
3. Open <https://github.com/qamran/Messkonzept-Copilot/settings/environments> → **production** → **Environment secrets** → **Add environment secret**: name `VERCEL_TOKEN`, value the token → **Add secret**.

**Check (agent):** `gh api repos/qamran/Messkonzept-Copilot/environments/production/secrets --jq '.secrets[].name'` lists `VERCEL_TOKEN` (only the name is visible, never the value); `gh api repos/qamran/Messkonzept-Copilot/actions/secrets --jq .total_count` gives 0 (no repository-wide secrets).
