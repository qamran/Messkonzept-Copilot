# MKC-10 plan: continuous deployment (k3s + Vercel)

**Ticket:** MKC-10 (#10). **Branch:** `mkc-10-cd`.

**Goal:** a merge to `main` deploys the backend to k3s over SSH, checks it, rolls it back on failure, and then deploys the frontend to Vercel production.

## Checked before starting (25.11.2026)

- Vercel project `messkonzept-copilot`, team slug `qamran`. Production alias `messkonzept-copilot.vercel.app` (public, HTTP 200). Preview URLs (`messkonzept-copilot-<hash>-qamran.vercel.app`, `messkonzept-copilot-git-<branch>-qamran.vercel.app`) are behind Vercel Authentication (HTTP 302): only the user can open them.
- The project has `gitProviderOptions.createDeployments: disabled`, so PRs get no preview yet, against the runbook. Fix: `vercel.json` turns off `main` only, then Git deployments are switched on again.
- `VERCEL_TOKEN` lives only in the `production` environment. Previews come from Vercel's Git integration, not from our workflows.
- `backend/.env` `DATABASE_URL` points at the Supabase Session pooler (`…pooler.supabase.com`).
- The image `:<sha>` exists only for commits on `main` (the CI job `publish`).

## Design choices

- **Origins (decision 45):**
  - `MKC_CORS_ORIGINS` keeps the exact list (production alias `https://messkonzept-copilot.vercel.app`).
  - New `MKC_CORS_ORIGIN_REGEX`: one anchored pattern for the previews, used by CORS **and** the token's `azp` check. Otherwise a preview passes CORS but its token is refused.
  - Pattern: `^https://messkonzept-copilot-[a-z0-9-]+-qamran\.vercel\.app$`. https only, project prefix, team suffix.
  - Accepted risk: `*.vercel.app` names are first come, first served. A team whose slug ends in `-qamran` could build a matching host. It still can't get a user's Clerk session for our instance. Recorded in ADR 002.
- **Version warning (decision 46):**
  - CD builds the frontend with `VITE_COMMIT=<sha>`. The frontend fetches `/api/version` and shows a warning when the API's `commit` differs.
  - No `VITE_COMMIT` (local, previews) means no check: previews call the production API and would always warn.
  - A failed fetch shows nothing and never breaks the page.
- **Restricted deploy user:**
  - Linux user `mkc-deploy`, no password, no sudo. `authorized_keys`: `restrict,command="/usr/local/bin/mkc-deploy"`.
  - `mkc-deploy` (root-owned, from `deploy/vm/mkc-deploy`) reads `SSH_ORIGINAL_COMMAND` and accepts only `deploy <40-hex sha>`, `rollback` and `status`. Anything else is refused.
  - `deploy`: downloads the chart at that commit from `codeload.github.com/qamran/Messkonzept-Copilot` (fixed URL; no chart or values from the client), then `helm upgrade --install mkc … -n mkc -f /etc/mkc/values.yaml --set image.tag=<sha> --rollback-on-failure --wait --timeout 600s` (600 s > the worker's 300 s grace period, decision 42).
  - `rollback`: `helm rollback mkc` to the previous revision; with no earlier revision it fails with a clear message.
  - Kubernetes access: a ServiceAccount `mkc-deployer` bound to the built-in `admin` role in namespace `mkc` only. Its kubeconfig points at `https://127.0.0.1:6443`. No cluster-wide rights, no root.
  - Helm v4.3.1 for arm64 on the VM, checksum-checked.
- **Production values:** `deploy/vm/values-production.yaml` in the repo (no secrets): host `92-6-240-17.sslip.io`, issuer `letsencrypt-prod`, `existingSecret: mkc-secrets`, Clerk issuer, CORS. The admin installs it to `/etc/mkc/values.yaml`, so the deploy key can't change values.
- **Secret:** `mkc-secrets` (`DATABASE_URL`) created by the admin in namespace `mkc`, with the value piped over SSH stdin (never in argv or logs). `existingSecret` does not restart pods when it changes (MKC-9 N11): the runbook has the restart command.
- **Migrations (decision 47):** no Helm migration hook yet. The API and worker use no tables. The hook comes with the first ticket whose running code needs a table.
- **`cd.yml`:**
  - `on: push` to `main` only; guard `github.repository == 'qamran/Messkonzept-Copilot'` (the Turing mirror runs Actions too); `environment: production`; `permissions: contents: read`; concurrency group without cancel.
  - Job `backend`: wait for `:<sha>` in GHCR (anonymous, fail after 40 min, never fall back to `:main`); check 6443 times out from the runner; `scripts/cd_deploy.sh` (SSH deploy with a pinned `known_hosts` line, smoke test over real HTTPS with retries, `rollback` on failure, exit 1).
  - Job `frontend` (needs `backend`): `vercel pull`, `vercel build --prod` with `VITE_COMMIT`, `vercel deploy --prebuilt --prod`. Vercel CLI pinned.
  - Secrets: `DEPLOY_SSH_KEY` and `VERCEL_TOKEN`, environment secrets only. `check_workflows.py` allows secrets only in `cd.yml`, only in jobs with `environment: production`.
- **Evidence before merge:** `cd.yml` can only run after the merge. So the deploy and rollback run by hand through the same forced command and `cd_deploy.sh` (with the deploy key, before it goes into GitHub) on `main`'s commit `1f16ba8`. The forced failure: `MKC_SMOKE_EXPECT_COMMIT=wrong-commit`. After the merge, `/api/version` must return the merge commit.

## Tests

- MKC-10.1: pytest red first: CORS and `azp` accept the production origin and preview hosts; refuse `http://`, lookalikes (`messkonzept-copilot-x-qamran.vercel.app.evil.com`, `evil-messkonzept-copilot-x-qamran.vercel.app`, other team suffix), and anything when the regex is empty.
- MKC-10.2: vitest red first: warning on a mismatch; none on a match; none without `VITE_COMMIT`; none when the fetch fails. `scripts/check_vercel.py` (or a check in an existing script) for `vercel.json`: `main` off, SPA rewrite.
- MKC-10.3: `scripts/test_mkc_deploy.sh` red first: runs `mkc-deploy` with stub `helm` and `curl` and checks that a shell, an arbitrary command, a short or non-hex sha and extra arguments are refused, and that `deploy <sha>` calls Helm with the fixed values file and timeout. On the VM: the same refusals over SSH with the real key.
- MKC-10.4: `check_workflows.py` red first (cd.yml rules); `cd_deploy.sh` drill (good deploy, forced failure → rollback, `/api/version` back on the earlier revision); 6443 timeout from outside.

## Done when

- After the merge: `cd.yml` run green, `https://92-6-240-17.sslip.io/api/version` returns the merge commit, the Vercel production site loads, the version warning is not shown.
