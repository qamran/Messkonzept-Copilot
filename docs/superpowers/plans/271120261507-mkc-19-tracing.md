# MKC-19 plan: Tracing (Langfuse + run log)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Ticket:** MKC-19 (#19). **Branch:** `mkc-19-tracing`.

**Goal:** every model call and tool call is inspectable, with tokens, cost, latency and errors.

**Spec:** design doc 8.5 ("Traces"), feature 23; backlog notes on MKC-18 and MKC-19; the review findings tagged MKC-19 in HANDOFF (18#1, 18#3, 13#4, 14#6).

**Architecture:**

- `mkc.observability.trace` (new):
  - `Tracer(sessions, sink)`: `span_model(CallTrace)`, `span_tool(ToolTrace)`, `span_stop(StopEvent)`, `outage(run_id, detail)`, `start_run(run_id) -> trace_id`, `flush()`
  - one record path: each event becomes one `TraceRecord`, written to the `run_log` table and sent to the sink; each side guarded on its own, so a failure never reaches the run
  - `Sink` (protocol): `send(record, trace_id)`, `flush()`. `LangfuseSink` wraps the Langfuse SDK; `None` when no keys are set (CI, replay, local): `run_log` still runs
- `mkc.models.client` (change): `CallTrace` gets `scope: TraceScope | None` (`run_id`, `item_id`, `step`); the four methods take a keyword `scope=` that never enters the replay key
- `mkc.harness.tools` (change): `ToolTrace` gets `run_id`, `item_id`, `step` from `ToolEnv` (`ToolEnv` gains `step`)
- `mkc.harness.loop` (change): passes the scope to every model call and the step to every tool env; finding 18#1 fixed
- `mkc.worker` (change): `main` builds one `Tracer`; the executor sets the trace id, passes the hooks, writes the outage row, flushes after each run and on shutdown

## Global constraints

- Migrations are additive only (decision 48): `0010_tracing` adds `run.trace_id` (text, nullable) and the table `run_log`.
- `run_log` has no foreign keys: an insert would take `FOR KEY SHARE` on the run row, which waits for the `FOR UPDATE` of `fence`. A log must never wait for, or block, the loop.
- The tracer writes with its own short session from `sessions`, never the loop's: model hooks fire on the `mkc-model-call` thread, and the loop's commits and fences stay as they are.
- No "current item" state on the tracer and no context variables: a call abandoned at the deadline can report after the loop moved on, so every event carries its ids by value.
- Commits under 200 lines; a red test before its code, failing on an assertion, not an `ImportError`; HANDOFF in every commit with clock times from git; no blank line between `Refs:` and `Co-Authored-By:`; each sub-issue `In progress` before its first commit.

## Decisions taken in this ticket

### Decision 59: tracing (taken by the development agent)

1. **One trace per run.** `run.trace_id` is a random 32-hex id, set once by `start_run` if it is NULL (like `start_clock`), so a resume by another worker reuses it. Not derived from the run id: local run 1 and production run 1 would share a trace in one Langfuse project. Langfuse gets `environment` (`MKC_LANGFUSE_ENVIRONMENT`, default `development`) and `release` = the build commit.
2. **What is traced:** every model call attempt (a retried call is one row per attempt), every tool call, every stop (`StopEvent`) and every database outage the worker waits out (the durable record that MKC-17 finding 1 asked for). One `run_log` row and one Langfuse observation per event: model calls are generations, tool calls are tool observations, stops and outages are events.
3. **Metadata only.** No prompts, model replies, tool arguments or PDF text go to Langfuse: the model route has zero data retention (decision 52), and Langfuse Cloud keeps what it gets. Sending content would be the user's call. Tool names are cut to 100 characters and error text to 500 (finding 14#6), since the text now leaves the machine.
4. **Cost:**
   - a failed call is recorded with its error and latency and no tokens or cost; the tracer does not estimate it (known limit of decision 58)
   - a call abandoned at the turn deadline that later returns is traced with its usage, on its own item and step: the trace has the cost that `turn.cost_eur` lost
   - replayed calls (`mode = replay`) carry the recorded cost in `run_log` with `mode`, and send no cost to Langfuse (finding 13#4); spend sums filter `mode = 'live'`
5. **Latency in Langfuse:** the hooks fire after the call, and the SDK sets a span's start when it is created. The span starts when the trace arrives and ends `latency_ms` later, so its duration is right and it sits shifted by that much; `latency_ms` is also in the metadata and in `run_log`.
6. **Failure safety:** the tracer catches every error of each sink on its own and logs it. The Langfuse SDK exports in a background thread; `flush` after each run and on shutdown is bounded by `MKC_LANGFUSE_TIMEOUT_SECONDS` (5; measured: an unreachable host makes `flush` return after the timeout).
7. **Finding 18#1:** `process_run` checks the run limits only when an item is left to serve, so a run whose last item ends on the turn that reaches a limit settles instead of stopping.

## Sub-issues

As built: the Langfuse SDK becomes the global OpenTelemetry provider and its default filter exports other libraries' `gen_ai.*` spans (the Anthropic SDK traces its calls with the prompt), so `make_client` passes `should_export_span=is_langfuse_span` (found by the pre-PR advisor check). The demo also checks the keys with `auth_check` and reads the trace back (`LangfuseSink.observations`), so a trace id in Postgres is not taken as proof. `build_executor` takes an optional `sink`. The span-duration test allows the few ms the SDK needs to build a span. The user set up Langfuse step by step (runbook "Set up Langfuse").
