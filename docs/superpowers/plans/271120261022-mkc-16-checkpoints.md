# MKC-16 plan: Turn checkpoints, resume, tool cache, idempotency

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Ticket:** MKC-16 (#16). **Branch:** `mkc-16-checkpoints`.

**Goal:** an interrupted run resumes at its last complete turn without repeating completed work or side effects.

**Spec:** design doc section 8.3 (checkpoints and resume), 8.2 (states), 8.5 (baseline switches); features 18 and 19.

**Architecture:** package `mkc.harness`.

- `mkc.harness.checkpoint`:
  - `save_turn(session, turn: TurnRecord, *, blobs: BlobStore, inline_max_bytes: int) -> None`: checks that calls and results pair one to one, moves large results to the blob store, adds the `turn` row. It does not commit; the loop commits (the last turn together with the state change).
  - `load_resume_context(session, item_id, *, blobs: BlobStore) -> ResumeContext`
- `mkc.harness.blobs`: `BlobStore` protocol (`put(data: bytes) -> str`, `get(ref: str) -> bytes`), refs `blob:sha256:<hex>`; `DbBlobStore` (table `blob`).
- `mkc.harness.cache`: `ToolCache(sessions, code_version)` (its own short sessions) with `get(tool, args, document_hash) -> Cached | None` and `put(...)`; `ToolRegistry.execute(call, ctx, env, cache=None)` does the lookup.
- `mkc.harness.drafts`: `make_save_draft(sessions)` (the real `save_draft`, upsert by key) and `record_key(env) -> tuple[str, str]`.
- `mkc.harness.loop` (change): `run_item` starts from `load_resume_context`; `process_run` resumes orphaned `running` items first.

## Global constraints

- Migrations are additive only (decision 48): `0005_blob`, `0006_tool_cache`, `0007_draft`.
- Every model call through `ModelClient`; tools get only `(args, env)`; the model never sets ids (decision 54).

## Decisions taken in this ticket

### Decision 56: checkpoint store, resume, cache key, tool database access

1. **Large outputs.** A tool result whose JSON is over `MKC_TURN_INLINE_MAX_BYTES` (default 16384) is stored in a `BlobStore`; the turn row keeps `{"ref": "blob:sha256:<hex>", "bytes": n}` instead of `result`.
   - No Storage bucket exists yet (a user task tied to MKC-21). The interim backend is the Postgres table `blob` (content-addressed, `sha256` primary key, `bytea`). It is durable in production today and in the nightly backup.
   - Size risk is small: turn results hold text and table JSON (tens of KB). Rendered images (MKC-23) go to the store as image refs, and MKC-21 adds a Supabase Storage `BlobStore` and swaps the default. Refs stay valid across the swap (same `sha256`).
2. **Resume.** An interrupted item stays `running`; no new state edge (design 8.2 is corrected to say so).
   - `process_run` serves the run's `running` items before `next_item`. That is safe only with one worker per run, which MKC-17's lease guarantees (and the worker Deployment has one replica, `Recreate`). `uq_turn_item_number` is the backstop: a second writer gets an `IntegrityError`, which propagates and never fails the item.
   - Turn number, step count and cost continue from the stored turns, so `MKC_ITEM_MAX_STEPS` counts across crashes.
   - **Resume context** (design 8.3): system prompt; **one** user message with the item task and, when more than one turn is stored, a compact summary of the earlier turns built in code (no model call), wrapped as data in `<earlier_turns>`; then the last turn's assistant message and its tool messages, rebuilt with `wrap_tool_result`. One user message avoids two user messages in a row, which not every provider accepts.
   - A turn in flight when the crash happened has no row, so it is discarded and re-requested. Its model cost is lost from `turn.cost_eur` (known limit; MKC-19's trace still has it).
3. **Tool cache.** Cached tools are named, not inferred: `Tool.cacheable` (default `False`); `extract_text`, `extract_tables` and `render_region` set it (design 8.3). `validate_draft` and `segment_document` are deterministic but not cached (they depend on reference data or run once). `ToolRegistry` refuses `cacheable` without `deterministic`.
   - Key: `(tool, code_version, sha256(canonical JSON of the call's args), document_hash)`. `code_version` is `Settings.commit` in the worker. After a code fix a new commit misses the cache, so the eval loop (decision 55) never scores a pre-fix result; the eval runner (MKC-31) must pass the git `HEAD` commit, not `dev`.
   - Only `ok` results are stored (`ON CONFLICT DO NOTHING`), and each write **commits on its own**, before the turn checkpoint. Completed turns are never re-executed, so the hits on resume come from the discarded in-flight turn.
   - A hit goes through the registry's tracers with `cached=True` on `ToolTrace`.
4. **How tools reach the database.** A factory at registry build: `default_registry(tracers, *, sessions: sessionmaker[Session] | None = None)`. With `sessions`, `save_draft` is the real one; without, it stays the placeholder. `ToolEnv` stays ids only. MKC-22 and MKC-23 follow the same pattern.
5. **Idempotency.**
   - `save_draft`: table `draft`, unique `(document_hash, concept_key)` from `ToolEnv` (`record_key(env)`; review finding 8 of PR #131). A second save upserts the body and keeps one row. A draft row can outlive a failed item; later code goes by the item state, not by the row. What a save does after enqueue or approval is MKC-23's.
   - `commit_record`: there is no catalogue yet. The key is the same `record_key` (design 8.2: document hash, concept number). **MKC-29/30 must** put a unique constraint on it in the catalogue table and test a double commit. Disclosed in the PR.
6. **Baseline seams (MKC-20).** One switch each: `run_item(..., code_version: str | None)` (None = cache off); checkpoints and resume through `load_resume_context` (MKC-20 passes a flag that ignores stored turns); idempotency through the draft table's key.

## Review focus

- Two user messages in a row: avoided by design (one user message); the resume test asserts the order.
- A crash loop must not reset the step cap: asserted in `test_crash_after_turn_k_resumes_at_k_plus_1`.
- A stale cache after a code fix: asserted by the `code_version` miss test.
- A draft row of a failed item: documented; no code reads drafts yet.
- Two writers on one item: the unique key raises; asserted in MKC-16.3.

## Rulings during the build

Choices the plan left open, taken while building (each is also in the PR body):

- **Prompt helpers moved** to `mkc.harness.prompts` (system prompt, `task_message`, `wrap_tool_result`, `earlier_turns`): the checkpoint module needs them, and importing them from `loop` would be circular. `loop` re-exports the old names.
- **`run_item(code_version=...)`** instead of a `cache` argument: the loop builds `ToolCache` on its own session, so callers can't pass a cache bound to another session. `None` switches the cache off.
- **The cache lookup lives in `ToolRegistry.execute`**, after the allow-list and argument checks, so a hit is traced like any call (`ToolTrace.cached=True`). The key hashes the validated arguments (`model_dump(mode="json")`), so `{"page": 1}` and `{"page": "1"}` share a row. A cache database error propagates like every database error in the loop; a result with no JSON form is not cached.
- **The summary** of an earlier turn lists each call's tool, arguments and `ok`, plus the error code of a failed call. `result_ref` entries keep `ok`, so the summary never reads a blob.
- **`ResumeContext(messages, next_number, steps_done, cost_eur)`**: `steps_done` is the last stored turn number.
- **`save_draft`** returns `{"draft_id": <id>}`, the same id for every save of one key; a second save replaces the body and the `item_id`.
- **Tests that passed on their first run** pin behaviour the change must keep: the last turn and the end state in one commit (`_finish` already did it), zero stored turns is a fresh start, a second writer raises `IntegrityError`, three no-cache cases, and `default_registry()` without `sessions` keeps the placeholder.
- **Pre-PR review (fresh agent):** no Critical. Fixed: `process_run` passes `inline_max_bytes` and `code_version` to `run_item`; `ToolCache` takes a `sessionmaker` and never commits the loop's session. Deferred with backlog notes: a resume-attempt cap (MKC-18), NUL characters in PDF text (MKC-22), the draft key spanning runs (MKC-23). Not changed: a failed result has no data and a message of at most 1000 characters, so it is never stored as a ref; the lost cost of an in-flight call is documented in design 8.3.
- **After an advisor check:** a database error inside a tool call (a cache read or write) propagated out of `execute` but was then turned into `tool_error` by the loop; `_run_calls` now lets `SQLAlchemyError` through, so the item stays `running` and resumes (`test_a_database_error_in_a_tool_call_propagates_and_the_item_can_resume`). The one-commit test now records what each commit carries; a mutant that commits the last turn before the state change fails it.
