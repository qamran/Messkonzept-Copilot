# MKC-11 plan: backups and restore drill

**Ticket:** MKC-11 (#11). **Branch:** `mkc-11-backups` (code), then a docs branch for the drill.

**Goal:** a nightly database backup goes off-site to Oracle Object Storage with 14 days of retention, a failed backup is visible, and one restore is proven.

## Checked before starting (26.11.2026)

- Supabase runs PostgreSQL 17.12 (aarch64). Debian trixie (the image's base) ships `postgresql-client-17` 17.12-0+deb13u1, the same major version. `pg_dump` must not be older than the server.
- pgvector is available on Supabase but not installed: migration 0001 has never run there. `CREATE EXTENSION IF NOT EXISTS vector` is idempotent.
- The Oracle VM runs in `eu-frankfurt-1`.
- Production `public` has no tables yet. After PR A it holds `alembic_version` and `backup_runs`. The catalogue and gold tables come in later tickets, so the drill compares every table in `public`, whatever exists then. Production is not seeded for the drill.

## Design choices

- **Upload (decision 49):** a bucket pre-authenticated request (PAR) with "permit object writes" only, limited to the prefix `nightly/`. It can't read, list or delete. A leaked link can't expose or destroy backups. It expires: the runbook names the date and the renewal steps. The link is a secret (`MKC_BACKUP_UPLOAD_URL` in `mkc-secrets`), stored by the admin over SSH stdin.
- **Retention:** an Object Storage lifecycle rule deletes `nightly/` objects after 14 days. It needs the IAM policy `Allow service objectstorage-eu-frankfurt-1 to manage object-family in tenancy`. Evidence in this ticket: the rule exists. That an old object is really deleted can only be seen after 14 days; checked in a later session and logged.
- **Dump:** `pg_dump --schema=public --no-owner --no-privileges` (plain SQL), gzip. A full Supabase dump (roles, `auth`, `storage`) does not restore into a plain Postgres. Extensions are not in `public`; the restore creates `vector` first.
- **The command `mkc-backup`** (Python, in the backend image):
  - writes the dump to `MKC_BACKUP_DIR` (an `emptyDir` with a size limit; the root file system is read-only), then PUTs the file with a known `Content-Length` to `<link>nightly/mkc-<UTC time>.sql.gz`
  - fails closed: a non-zero `pg_dump` exit never uploads and never records success
  - records the run in `backup_runs`: a row `running` at the start, then `ok` (object name, size, finish time) or `failed` (error class and a short message). A failed status write is logged but does not stop the upload.
  - the upload link and the database password never appear in argv, logs, exceptions, the status row or the endpoint. The password goes to `pg_dump` by environment (`PGPASSWORD`), not in the command line.
  - one JSON log line per run; exit 0 ok, 1 failed
- **Status endpoint:** `GET /api/admin/backup-status` (admin only): `{"state": "never" | "ok" | "failed" | "running", "last_run": …, "last_success": …, "stale": bool}`. `stale` is true when the last success is older than 26 hours (or there is none), so a job that never starts is visible too.
- **Migrations on deploy (decision 48, changes decision 47):**
  - a Helm hook Job (`pre-install,pre-upgrade`) runs `alembic upgrade head` with the same image and the same secret before any pod changes. A failed migration fails the Helm upgrade, and `--rollback-on-failure` keeps the old release.
  - migrations are additive only (new tables and columns, never drop or rename in the same release): `helm rollback` does not undo a schema change, so the previous release must keep working on the new schema.
  - on a fresh install the hook runs before the chart's own Secret and ConfigMap exist. The kind smoke test covers a fresh install, so this case is tested, not only the production upgrade with `existingSecret`.
- **CronJob:** off by default in the chart, on in `deploy/vm/values-production.yaml`. Schedule 03:30 `Europe/Berlin`. `concurrencyPolicy: Forbid`, `startingDeadlineSeconds`, `activeDeadlineSeconds`, `backoffLimit: 1`, history limits. Pod Security `restricted` (non-root uid 10001, read-only root, no privilege escalation, all capabilities dropped, seccomp `RuntimeDefault`).
- **Order on the VM before PR A's deploy:** the admin adds `MKC_BACKUP_UPLOAD_URL` to `mkc-secrets` first, then the new `/etc/mkc/values.yaml`. `mkc-deployer` (role `admin` in `mkc`) can create CronJobs and Jobs (checked with `can-i` before the merge).

## Tests

- MKC-11.1: pytest red first: migration 0002 creates `backup_runs` and is reversible; `alembic upgrade head` twice is a no-op. `check_helm.py` red first: the migration hook Job exists with hook annotations, the restricted security context and the same secret. kind: a fresh install runs the hook and the API comes up.
- MKC-11.2: pytest red first: a failing `pg_dump` → no upload, row `failed`, exit 1; an upload error → row `failed`; success → row `ok` with size and object name; the link and the password never appear in logs, the row or exceptions; a failed status write does not stop the upload. `check_containers.py`: the image has `pg_dump` 17.
- MKC-11.3: pytest red first: 401 without a token, 403 for a non-admin; `never` with `stale: true` on an empty table; `ok` and `stale: false` after a fresh success; `stale: true` after 27 hours; `failed` shows the last success separately.
- MKC-11.4: `check_helm.py` red first (CronJob rules, off by default); Compose smoke: `mkc-backup` against the stack's database, upload to a stub receiver, restore the received file into a second database, row counts match. kind: the CronJob renders and is admitted with Pod Security `restricted`.
- MKC-11.5: in production: a Job from the CronJob → an object in `nightly/`; `/api/admin/backup-status` shows `ok`; the restore drill into a throwaway Postgres 17 (Docker) matches the row counts of every `public` table.
