# MKC-17 plan: Run executor (worker with lease)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Ticket:** MKC-17 (#17). **Branch:** `mkc-17-run-executor`.

**Goal:** exactly one worker processes a run, survives restarts and deploys, and waits out database outages.

**Spec:** design doc section 8.4 (run executor), 8.2 (states), 8.3 (resume); feature 20; Review Focus 4 of the backlog.

**Architecture:** package `mkc.worker`.

- `mkc.worker.lease` (database functions; the caller commits):
  - `claim_run(session, *, owner, lease_seconds) -> Run | None`
  - `renew_lease(session, run_id, *, owner, lease_seconds) -> bool`
  - `release_lease(session, run_id, *, owner) -> None`
  - `fence(session, run_id, *, owner) -> None`: raises `LeaseLost` unless `owner` still holds the lease
  - `mark_waiting(session, run_id, *, owner) -> bool`
- `mkc.worker.executor`:
  - `Executor(settings, *, sessions, client_factory, owner=None)` with `run_once() -> bool` (claim, process, release), `graceful_shutdown()`, and a heartbeat thread (file heartbeat and lease renewal)
  - `claim_run()` is re-exported here, as the ticket names it
- `mkc.harness.loop` (change): `process_run` and `run_item` take `should_stop` and `fence` callables.
- `mkc.worker.main` (change): the poll loop runs `Executor.run_once`; SIGTERM calls `graceful_shutdown`.

## Decisions taken in this ticket

### Decision 57: lease, heartbeat, graceful stop, database outages

1. **Lease on the run row.** Two nullable columns on `run`: `lease_owner` (text, `<host>-<pid>-<random>`) and `lease_expires_at` (timestamptz). All times come from the database clock (`now()`), never the pod's.
   - `claim_run`: the oldest run in `running` or `waiting_for_database` whose lease is free, expired or already its own, `FOR UPDATE SKIP LOCKED`; it sets the owner and `now() + lease`. A run in `waiting_for_database` goes back to `running` in the same transaction.
   - `SKIP LOCKED` covers a claim that is not committed yet; the lease condition covers a committed claim.
   - **Fencing:** before every commit of a turn, an item end state or a new item claim, the loop calls `fence`, which locks the run row and raises `LeaseLost` if the worker no longer holds the lease. So a worker whose lease expired and was taken over can never add a turn. `uq_turn_item_number` stays as the backstop.
2. **Heartbeat thread.** One background thread for the worker's whole life:
   - touches the heartbeat file every `MKC_WORKER_POLL_SECONDS`, so the liveness probe stays green during a long model call or an outage
   - renews the lease every `MKC_WORKER_LEASE_RENEW_SECONDS` while a run is held (own short session; `WHERE lease_owner = me`)
   - renewal returns no row: the lease is lost, the run stops after the current turn (and `fence` stops any commit). A renewal that fails with a database error is not a lost lease; it is logged and retried.
3. **Timings** (settings, documented in the runbook):
   - `MKC_WORKER_LEASE_SECONDS` = 120: a crashed worker's run is taken over after at most 2 minutes
   - `MKC_WORKER_LEASE_RENEW_SECONDS` = 20; at least three renewals fit into one lease (checked at start)
   - `MKC_WORKER_DB_BACKOFF_MAX_SECONDS` = 30: database probes back off 1, 2, 4 … 30 s
   - `MKC_DATABASE_CONNECT_TIMEOUT_SECONDS` = 10, plus TCP keepalives on the engine, so a paused database fails instead of hanging
4. **Graceful stop.** `graceful_shutdown()` sets a stop flag. The loop checks it after each committed turn and before claiming the next item; the item stays `running` (no new edge, decision 56) and the run is not settled. The executor then releases the lease, and the next worker resumes at once. A turn that runs over the 300 s grace period is killed; its lease expires and the next worker resumes from the last checkpoint. A wall-clock turn deadline (MKC-13 finding 3) is a run limit and goes to MKC-18.
5. **Database outages** (`waiting_for_database`):
   - On a database error, the executor discards the session and probes with `SELECT 1`. A probe that works means it was not an outage: the error is logged, the lease released, and the worker carries on. A probe that fails starts waiting mode.
   - Waiting mode: the worker logs `database unavailable, waiting`, probes with backoff (sleeping on the stop flag, so SIGTERM still ends it), and keeps the file heartbeat.
   - **What "the run shows `waiting_for_database`" means:** nothing can be written while the database is down. On the first successful probe the worker writes `running -> waiting_for_database` (if it still holds the lease or nobody took the run), commits, then claims the run again (`waiting_for_database -> running`) and resumes from the last complete turn. So every outage the worker saw leaves its mark in the run's history, and the run shows `waiting_for_database` to a reader whose own connection works (an outage of the worker's path only). The test checks the history with a test-only trigger.
   - SIGTERM during an outage cannot release the lease; the worker exits anyway and the lease expires.
6. **Setup errors** (`ModelConfigError`, `ReplayMiss`): the executor logs them, releases the lease and waits `MKC_WORKER_DB_BACKOFF_MAX_SECONDS` before the next claim, so it does not spin. MKC-18 turns them into a run stop.
7. **The model client** is built only when a run is claimed, so a worker without model settings or a database (kind, Compose) still starts, stays healthy and stops cleanly.
8. New edges: `running -> waiting_for_database` and `waiting_for_database -> running`.
