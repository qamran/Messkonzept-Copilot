# Architecture Decision Record (ADR) 002: Frontend on Vercel, backend on k3s (Oracle Cloud Always Free)

- **Status:** accepted
- **Date:** 24.11.2026
- **Design reference:** design doc section 13

## Context

The app has two parts that behave very differently:

- **Frontend:** a static React build (Vite, shadcn/ui, Clerk).
- **Backend:** FastAPI plus the agent harness, with long-running, resumable extraction runs that pause for approvals.

The user wants a real DevOps setup (Docker, Kubernetes, GitHub Actions), a deployed app that stays online after the course, and no hosting cost. The user has an Oracle Cloud Always Free account with a running ARM VM. Streamlit is ruled out.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| Everything on k3s | One deploy target, one pipeline, "full stack on Kubernetes" | No preview deployments; the frontend goes down with the server |
| **Frontend on Vercel + backend on k3s** | Preview URL per PR; global CDN and automatic HTTPS; the frontend stays up if the server is down; less load on the free VM | Two deploy targets; needs CORS, two sets of environment variables, Clerk for both domains, and version sync |
| Backend on Vercel too | One platform | Serverless time limits and no persistent process; unsuitable for long, resumable runs |
| Managed Kubernetes (GKE, AKS, DOKS) | More "enterprise" | Paid after trial credits |
| PaaS (Render, Fly) | Simple | No Kubernetes showcase |

## Decision

- **Frontend on Vercel:** preview per PR, production on merge to `main`.
- **Backend on k3s** on the Oracle Always Free ARM VM, deployed with a Helm chart. Images are multi-arch on GHCR, and the chart is tested on kind in CI before each deploy.

## Consequences

- **CORS allow-list:** the production Vercel domain plus the preview pattern. `VITE_API_URL` is set per Vercel environment. Clerk is configured for both domains.
- **Previews use the production backend.** Only admin users can start runs or approve.
- **Version sync:** `/api/version` plus a warning in the frontend. CD deploys the backend before promoting the frontend, followed by a post-deploy smoke test and rollback.
- **Vercel Hobby** is for non-commercial use, which fits a capstone; a commercial product would need a paid plan.
- **Backend process split** (added 24.11.2026 after independent review): one image with two Deployments: a stateless API (may scale) and a **single-replica harness worker** that claims runs through a Postgres lease. On SIGTERM during `helm upgrade`, the worker finishes its turn, checkpoints and releases the lease. Loss of the single VM means downtime, not data loss.
- **CD hardening for a public repo** (added 24.11.2026):
  - No secrets in workflows triggered by fork PRs; `pull_request_target` is not used.
  - Deploys run only on pushes to `main`, inside a protected `production` environment.
  - The k3s API is not exposed to the internet: CD connects over SSH to a restricted deploy user that runs `helm upgrade`.
- **Clerk:** settled on 25.11.2026 (MKC-7): the development instance for every environment. See "Clerk instance" below.
- **Fallback** if k3s blocks deployment: Compose on the same VM, with the chart still tested on kind in CI.

## Continuous deployment (added 25.11.2026, MKC-10)

**Decision (agent; decisions 45–47):** `.github/workflows/cd.yml` deploys every merge to `main`: first the backend to k3s over SSH, then the frontend to Vercel production. Steps and the drill: runbook "Deploy and rollback".

**How the backend gets deployed:**

- The k3s API (6443) stays closed. GitHub Actions reaches the VM only over SSH, as the user `mkc-deploy`.
- The deploy key is limited in `authorized_keys`: `restrict,command="/usr/local/bin/mkc-deploy"`. No shell, no port forwarding, no files.
- `mkc-deploy` accepts only `deploy <40-hex commit>`, `rollback` and `status`. The commit must be on `main` (GitHub's compare API: `behind` or `identical`), because GitHub also serves a fork's commits under our repository's URL. The chart comes from GitHub at that commit; the values from root-owned `/etc/mkc/values.yaml`. The client chooses nothing else.
- Namespace `mkc` enforces Pod Security `restricted`: no privileged, root or host-mounting pods, whatever a chart asks for.
- Kubernetes rights: the `admin` role in namespace `mkc` only (ServiceAccount `mkc-deployer`).
- Helm: `upgrade --install --rollback-on-failure --wait=watcher --timeout 600s` (longer than the worker's 300 s grace period, decision 42).
- `scripts/cd_deploy.sh` smoke-tests `/health` and `/api/version` over HTTPS and runs `rollback` when they fail.

**Options considered for reaching the cluster:**

| Option | Result |
|---|---|
| Open 6443 to GitHub's IP ranges, kubeconfig in a secret | Rejected: the API on the internet; GitHub's ranges are large |
| A self-hosted runner on the VM | Rejected: runs workflow code on the server; a risk for a public repo |
| SSH with a full shell for the deploy user | Rejected: a leaked key would be a shell on the server |
| **SSH with a forced command** | Chosen: a leaked key can only deploy a commit that is on our `main`, roll back, or read the status |

**Frontend:** `vercel build` and `vercel deploy --prebuilt --prod` in the CD job, after the backend. `frontend/vercel.json` stops Vercel's Git integration from deploying `main`; it still builds a preview per PR. Previews are behind Vercel Authentication (only the user can open them).

**Origins (decision 45):** the production site is listed exactly; one pattern adds the previews to CORS **and** the token's `azp` check: `^https://messkonzept-copilot-[a-z0-9-]+-qamran\.vercel\.app$`. (Deploys need two approvals in the `production` environment: `backend`, then `frontend`.) Accepted risk (stated after the PR #109 review; accepted by the user on 26.11.2026): a name pattern can't be made safe. Vercel gives every project the host `<project>.vercel.app`, first come, first served, so any Vercel account can create a project named `messkonzept-copilot-<x>-qamran` whose host matches. The Clerk publishable key is public, so such a page can show our sign-in; if a user signs in there, the page gets a token the API accepts with that user's rights. Not tested whether Clerk's development instance lets such a page finish a sign-in; assume it can. Rule: sign in only on the production site or on a preview opened from a PR in our repo; revisit before any real data or a Clerk production instance. Ways to remove the risk: drop previews from the `azp` check (previews then can't call signed-in endpoints), or put previews on a domain we own (decision 45).

**Version warning (decision 46):** the production build carries `VITE_COMMIT`; the page warns when `/api/version` reports another commit. Preview and local builds skip the check.

**Not yet:** database migrations on deploy (decision 47). The running code uses no tables; the first ticket that needs one adds a migration step.

## Server and API host (added 25.11.2026, MKC-10)

**Decisions:** decision 43 (user): API host `92-6-240-17.sslip.io`. Decision 44 (agent): the server setup. The step-by-step setup is in the runbook (`docs/251120261645-runbook.md`, "Server setup").

- **VM:** Oracle `VM.Standard.A1.Flex`, 4 OCPUs / 24 GB (the whole Always Free allowance), Ubuntu 24.04 arm64, ephemeral public IP `92.6.240.17`.
- **Firewalls:** ports 80 and 443 open in Oracle's security list and in the VM's iptables. Port 6443 (Kubernetes API) is never opened: CD will reach the cluster over SSH (design doc section 10). iptables also accepts the k3s pod and service ranges, and Oracle's FORWARD reject rule is removed, or the pod network breaks.
- **Cluster:** k3s v1.37.2+k3s1 (the stable channel) with Traefik; cert-manager v1.21.3 with HTTP-01 ClusterIssuers `letsencrypt-staging` and `letsencrypt-prod`, without an ACME e-mail.
- **API host:** sslip.io maps `92-6-240-17.sslip.io` to `92.6.240.17` with no DNS record.
  - Accepted limits: the name changes with the IP; Let's Encrypt rate limits may be shared with other sslip.io users.
  - Moving to an own domain later changes only the Helm values, `VITE_API_URL` and the CORS settings.
- **Vercel:** project `messkonzept-copilot` (root `frontend`, Vite, Node 24), connected to the repo for preview deployments. Production deploys come from the deploy workflow, after the backend (MKC-10).
- **GitHub:** environment `production` with the required reviewer `qamran`, protected branches only, and the secret `VERCEL_TOKEN`.

## Helm chart and kind test (added 25.11.2026, MKC-9)

**Decision (agent, decision 42):**

- **One chart,** `deploy/helm/mkc/`, for the API and the worker (same image, different command).
- **API:** replicas from values; startup, readiness and liveness probes on `/health`.
- **Worker:**
  - `replicas: 1` written in the template, not a value: one worker holds the Postgres lease (decision 26).
  - `strategy: Recreate`: the old pod stops before the new one starts.
  - Probes run `mkc-worker-health`. The worker has no HTTP port, so it touches a heartbeat file on every poll, and the command fails when the file is older than 30 s.
  - `terminationGracePeriodSeconds: 300`, the turn budget (below).
- **Both pods:** uid 10001 (as in the image), read-only root filesystem with `/tmp` as `emptyDir`, no privilege escalation, all capabilities dropped, no service-account token.
- **Secrets:** `secrets:` in values becomes a Secret, or `existingSecret` names one made outside the chart (production, MKC-10). `values.yaml` holds no secret values. Pods restart when the settings or the Secret change (checksum annotations).
- **Ingress:** class from values (k3s ships Traefik); TLS through the `cert-manager.io/cluster-issuer` annotation and a TLS secret name. cert-manager itself, and its `ClusterIssuer`, are installed outside the chart.
- **Image:** `image.tag` is required (a commit SHA); `latest` is refused.

**The turn budget (300 s):** on SIGTERM the worker finishes its turn, checkpoints and releases the lease (design doc 8.4).

| Part | Seconds |
|---|---|
| Model call (the `ModelClient` timeout must stay at or below this) | 180 |
| Tool calls in the turn | 60 |
| Checkpoint and lease release | 30 |
| Margin | 30 |
| **Grace period** | **300** |

MKC-10's `helm upgrade --timeout` must be longer than 300 s, or a deploy can time out while the old worker still finishes its turn.

**Heartbeat and long turns:** today the worker touches its heartbeat only between polls (max age 30 s; liveness fails after 3 × 30 s). Once a turn can take up to 240 s (MKC-17, MKC-20), the worker must also beat during a turn, or the max age must be raised; otherwise Kubernetes restarts a healthy worker mid-turn. **Done in MKC-17 (decision 57):** a thread of its own touches the file every poll interval for the worker's whole life, also during a turn, a database outage or a hanging lease renewal; the max age stays 30 s.

**The kind test:** CI job `kind`, on every PR, a required check; `publish` needs it.

- Helm 4.3.1, kind 0.33.0 and kubectl 1.37.0 as checksum-pinned release binaries; the kind node `v1.37.0` is pinned by digest (k3s stable is 1.37).
- `helm lint --strict`, then `scripts/kind_smoke.sh`: builds the image, loads it into kind, installs the chart with `ci-values.yaml` and checks `/health`, the commit from `/api/version`, the worker Ready without restarts, and a clean SIGTERM stop.
- The kind test has no database: nothing it checks touches the database yet. Migrations as a Helm hook come with the deploy (MKC-10) or the first table that needs them.

**Options considered:**

| Option | Result |
|---|---|
| Worker without probes | Ready as soon as the container starts, even while it crash-loops |
| Worker with an HTTP health port | A web server in the worker only for probes |
| **Heartbeat file + `mkc-worker-health` exec probe** | Chosen: small, and it fails when the poll loop hangs |
| Worker `RollingUpdate` | Two workers for a moment during each upgrade |
| **Worker `Recreate`** | Chosen: never two workers; the lease (MKC-20) is the real guard |
| Chart creates the cert-manager `Certificate` | kind has no cert-manager CRDs; the install would fail there |

## Images and the GHCR push (added 25.11.2026, MKC-8)

**Decision (agent, decision 41):**

- **One backend image** from `backend/Dockerfile`: a builder stage installs the locked dependencies and the `mkc` package into a venv; the runtime stage runs as uid 10001. Base images are pinned by their multi-arch index digest. `MKC_COMMIT` is a build argument and reaches `/api/version`. The default command is the API; the worker runs the same image with `mkc-worker`. `alembic.ini` and `migrations/` are in the image for later deploys.
- **Local stack:** `compose.yaml` with db, api, worker and frontend. The frontend image (Vite build behind an unprivileged nginx) exists only for local Compose; Vercel builds the deployed frontend.
- **On every PR**, the CI job `image` runs `scripts/compose_smoke.sh`, scans the image with Grype (checksum-pinned binary; high or critical with a fix fails) and builds `linux/amd64,linux/arm64` without pushing.
- **On a push to `main`**, the CI job `publish` pushes `ghcr.io/qamran/messkonzept-copilot-backend` with the tags `<commit sha>` and `main`.

**The narrowed write rule:** `scripts/check_workflows.py` refuses every write permission in CI, with one exception. `packages: write` is allowed only:

- in the job `publish` of `ci.yml`
- with the exact job-level guard `github.event_name == 'push' && github.ref == 'refs/heads/main' && github.repository == 'qamran/Messkonzept-Copilot'`

**Why:**

- **The guard:** a PR from a fork never reaches the job, and the Turing mirror (where Actions also run) does not try to push.
- **The login:** the job uses `github.token`, not a stored secret, so the "no secrets in CI" rule stays unchanged.
- **The `production` environment:** a push to GHCR is not a deploy, so the job does not need it. The deploy jobs (MKC-10 and later) still need their own narrowing in that environment.

**Options considered:**

| Option | Result |
|---|---|
| Separate publish workflow | A second place to keep the guard and the pins in step; `needs` on the CI jobs is not possible across workflows |
| Push from the `image` job with a step-level `if:` | The PR job would hold `packages: write`, even if unused |
| **Guarded `publish` job in `ci.yml`** | Chosen: the write permission exists only in a job that never runs on PRs or on the mirror |

## Clerk instance (added 25.11.2026, MKC-7)

**Decision (user):** the Clerk **development instance** is used for every environment, permanently: local, Vercel previews and Vercel production. No Clerk production instance is created.

**Why** (checked in Clerk's docs on 25.11.2026; docs-based, because no Vercel project exists yet):

- Clerk production keys can't be used on a host's preview domain such as `*.vercel.app`, and a production instance needs a domain you own.
- The only way to give previews production keys is Vercel's Preview Deployment Suffix (previews on a subdomain of your own domain). It needs Vercel Pro; the user has no Pro plan.
- A development instance works on any domain, so one instance covers local, previews and production. The backend trusts one issuer.

**Options considered:**

| Option | Result |
|---|---|
| Development instance for local and previews, production instance for production; backend trusts both issuers | Needs an owned domain; two issuers |
| Same, but previews read-only (development tokens never admin) | Needs an owned domain; no admin testing on previews |
| Production instance on previews via Vercel's Preview Deployment Suffix | Needs Vercel Pro (paid) and a domain |
| **Development instance everywhere** | Chosen: free, no domain needed for Clerk, one issuer |

**Accepted limits:**

- Clerk shows a "Development" badge on its sign-in screens.
- At most 100 users per development instance. Enough: only the user and a few reviewers sign in; the public demo needs no login.
- Clerk describes the development instance as having a relaxed security posture, "not suitable for production workloads". Accepted for a capstone; a real product would switch to a production instance on an owned domain.
- Google sign-in uses Clerk's shared OAuth credentials (no extra scopes needed).

**How it is wired:**

- **Admin role:** public metadata `{"role": "admin"}`, set only in the Clerk dashboard (users can't change public metadata). The session token carries it as the custom claim `"role": "{{user.public_metadata.role}}"`. The user's own Google account is the admin.
- **Backend** (`mkc.api.auth`): checks the RS256 signature with the instance's public keys (`<issuer>/.well-known/jwks.json`), plus `exp`, `nbf`, `iss`, `sub` and, when present, `azp` against an allow-list. Invalid tokens give 401, a non-admin on an admin route 403, and an unreachable JWKS 503. No Clerk secret key is used or stored. Settings: `MKC_CLERK_ISSUER`, `MKC_CLERK_AUTHORIZED_PARTIES`, `MKC_CORS_ORIGINS`.
- **Frontend:** `VITE_CLERK_PUBLISHABLE_KEY` (the development instance's `pk_test_` key) in every Vercel environment; `RequireAdmin` reads the same `role`.
- **Production CORS and `azp`:** done in MKC-10 (decision 45, section "Continuous deployment").
