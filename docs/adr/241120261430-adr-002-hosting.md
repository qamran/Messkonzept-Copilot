# Architecture Decision Record (ADR) 002: Frontend on Vercel, backend on k3s (Oracle Cloud Always Free)

- **Status:** accepted
- **Date:** 24.11.2026
- **Design reference:** design doc section 13

## Context

The app has two parts that behave very differently:

- **Frontend:** a static React build (Vite, shadcn/ui, Clerk).
- **Backend:** FastAPI plus the agent harness, with long-running, resumable extraction runs that pause for approvals.

The user wants a real DevOps setup (Docker, Kubernetes, GitHub Actions), a deployed app that stays online after the course, and no hosting cost. The user has an Oracle Cloud Always Free account with a running ARM VM. Streamlit is ruled out.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| Everything on k3s | One deploy target, one pipeline, "full stack on Kubernetes" | No preview deployments; the frontend goes down with the server |
| **Frontend on Vercel + backend on k3s** | Preview URL per PR; global CDN and automatic HTTPS; the frontend stays up if the server is down; less load on the free VM | Two deploy targets; needs CORS, two sets of environment variables, Clerk for both domains, and version sync |
| Backend on Vercel too | One platform | Serverless time limits and no persistent process; unsuitable for long, resumable runs |
| Managed Kubernetes (GKE, AKS, DOKS) | More "enterprise" | Paid after trial credits |
| PaaS (Render, Fly) | Simple | No Kubernetes showcase |

## Decision

- **Frontend on Vercel:** preview per PR, production on merge to `main`.
- **Backend on k3s** on the Oracle Always Free ARM VM, deployed with a Helm chart. Images are multi-arch on GHCR, and the chart is tested on kind in CI before each deploy.

## Consequences

- **CORS allow-list:** the production Vercel domain plus the preview pattern. `VITE_API_URL` is set per Vercel environment. Clerk is configured for both domains.
- **Previews use the production backend.** Only admin users can start runs or approve.
- **Version sync:** `/api/version` plus a warning in the frontend. CD deploys the backend before promoting the frontend, followed by a post-deploy smoke test and rollback.
- **Vercel Hobby** is for non-commercial use, which fits a capstone; a commercial product would need a paid plan.
- **Backend process split** (added 24.11.2026 after independent review): one image with two Deployments: a stateless API (may scale) and a **single-replica harness worker** that claims runs through a Postgres lease. On SIGTERM during `helm upgrade`, the worker finishes its turn, checkpoints and releases the lease. Loss of the single VM means downtime, not data loss.
- **CD hardening for a public repo** (added 24.11.2026):
  - No secrets in workflows triggered by fork PRs; `pull_request_target` is not used.
  - Deploys run only on pushes to `main`, inside a protected `production` environment.
  - The k3s API is not exposed to the internet: CD connects over SSH to a restricted deploy user that runs `helm upgrade`.
- **Clerk:** settled on 25.11.2026 (MKC-7): the development instance for every environment. See "Clerk instance" below.
- **Fallback** if k3s blocks deployment: Compose on the same VM, with the chart still tested on kind in CI.

## Clerk instance (added 25.11.2026, MKC-7)

**Decision (user):** the Clerk **development instance** is used for every environment, permanently: local, Vercel previews and Vercel production. No Clerk production instance is created.

**Why** (checked in Clerk's docs on 25.11.2026; docs-based, because no Vercel project exists yet):

- Clerk production keys can't be used on a host's preview domain such as `*.vercel.app`, and a production instance needs a domain you own.
- The only way to give previews production keys is Vercel's Preview Deployment Suffix (previews on a subdomain of your own domain). It needs Vercel Pro; the user has no Pro plan.
- A development instance works on any domain, so one instance covers local, previews and production. The backend trusts one issuer.

**Options considered:**

| Option | Result |
|---|---|
| Development instance for local and previews, production instance for production; backend trusts both issuers | Needs an owned domain; two issuers |
| Same, but previews read-only (development tokens never admin) | Needs an owned domain; no admin testing on previews |
| Production instance on previews via Vercel's Preview Deployment Suffix | Needs Vercel Pro (paid) and a domain |
| **Development instance everywhere** | Chosen: free, no domain needed for Clerk, one issuer |

**Accepted limits:**

- Clerk shows a "Development" badge on its sign-in screens.
- At most 100 users per development instance. Enough: only the user and a few reviewers sign in; the public demo needs no login.
- Clerk describes the development instance as having a relaxed security posture, "not suitable for production workloads". Accepted for a capstone; a real product would switch to a production instance on an owned domain.
- Google sign-in uses Clerk's shared OAuth credentials (no extra scopes needed).

**How it is wired:**

- **Admin role:** public metadata `{"role": "admin"}`, set only in the Clerk dashboard (users can't change public metadata). The session token carries it as the custom claim `"role": "{{user.public_metadata.role}}"`. The user's own Google account is the admin.
- **Backend** (`mkc.api.auth`): checks the RS256 signature with the instance's public keys (`<issuer>/.well-known/jwks.json`), plus `exp`, `nbf`, `iss`, `sub` and, when present, `azp` against an allow-list. No Clerk secret key is used or stored. Settings: `MKC_CLERK_ISSUER`, `MKC_CLERK_AUTHORIZED_PARTIES`, `MKC_CORS_ORIGINS`.
- **Frontend:** `VITE_CLERK_PUBLISHABLE_KEY` (the development instance's `pk_test_` key) in every Vercel environment; `RequireAdmin` reads the same `role`.
- **Production CORS and `azp`:** the production and preview Vercel origins are added to `MKC_CORS_ORIGINS` and `MKC_CLERK_AUTHORIZED_PARTIES` with the deploy tickets (feature 11).
