# Architecture Decision Record (ADR) 002: Frontend on Vercel, backend on k3s (Oracle Cloud Always Free)

- **Status:** accepted
- **Date:** 24.11.2026
- **Design reference:** design doc section 13

## Context

The app has two parts that behave very differently:

- **Frontend:** a static React build (Vite, shadcn/ui, Clerk).
- **Backend:** FastAPI plus the agent harness, with long-running, resumable extraction runs that pause for approvals.

The user wants a real DevOps setup (Docker, Kubernetes, GitHub Actions), a deployed app that stays online after the course, and no hosting cost. The user has an Oracle Cloud Always Free account with a running ARM VM. Streamlit is ruled out.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| Everything on k3s | One deploy target, one pipeline, "full stack on Kubernetes" | No preview deployments; the frontend goes down with the server |
| **Frontend on Vercel + backend on k3s** | Preview URL per PR; global CDN and automatic HTTPS; the frontend stays up if the server is down; less load on the free VM | Two deploy targets; needs CORS, two sets of environment variables, Clerk for both domains, and version sync |
| Backend on Vercel too | One platform | Serverless time limits and no persistent process; unsuitable for long, resumable runs |
| Managed Kubernetes (GKE, AKS, DOKS) | More "enterprise" | Paid after trial credits |
| PaaS (Render, Fly) | Simple | No Kubernetes showcase |

## Decision

- **Frontend on Vercel:** preview per PR, production on merge to `main`.
- **Backend on k3s** on the Oracle Always Free ARM VM, deployed with a Helm chart. Images are multi-arch on GHCR, and the chart is tested on kind in CI before each deploy.

## Consequences

- **CORS allow-list:** the production Vercel domain plus the preview pattern. `VITE_API_URL` is set per Vercel environment. Clerk is configured for both domains.
- **Previews use the production backend.** Only admin users can start runs or approve.
- **Version sync:** `/api/version` plus a warning in the frontend. CD deploys the backend before promoting the frontend, followed by a post-deploy smoke test and rollback.
- **Vercel Hobby** is for non-commercial use, which fits a capstone; a commercial product would need a paid plan.
- **Backend process split** (added 24.11.2026 after independent review): one image with two Deployments: a stateless API (may scale) and a **single-replica harness worker** that claims runs through a Postgres lease. On SIGTERM during `helm upgrade`, the worker finishes its turn, checkpoints and releases the lease. Loss of the single VM means downtime, not data loss.
- **CD hardening for a public repo** (added 24.11.2026):
  - No secrets in workflows triggered by fork PRs; `pull_request_target` is not used.
  - Deploys run only on pushes to `main`, inside a protected `production` environment.
  - The k3s API is not exposed to the internet: CD connects over SSH to a restricted deploy user that runs `helm upgrade`.
- **Clerk:** a production instance needs an owned domain. Whether Vercel preview domains can use it, or need Clerk's development instance, is verified in Phase 0.
- **Fallback** if k3s blocks deployment: Compose on the same VM, with the chart still tested on kind in CI.
