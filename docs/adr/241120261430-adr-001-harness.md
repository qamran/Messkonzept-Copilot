# Architecture Decision Record (ADR) 001: Custom agent harness on LangChain model and tool plumbing

- **Status:** accepted
- **Date:** 24.11.2026
- **Design reference:** `docs/superpowers/specs/241120261330-messkonzept-copilot-design.md`, sections 5.1, 6 and 8

## Context

The capstone brief (Case 5) asks for a **reusable agent harness** demonstrated on one domain workflow:

- a tool-calling loop through OpenRouter
- checkpoints and resume without repeating completed actions
- a tool allow-list and argument validation
- user approval for consequential actions
- limits on steps, time, cost and retries
- traces
- an **evaluation against a simple loop without checkpoints**

Our workflow is catalogue extraction: a durable queue of about 36 concept items over two operator PDFs, with vision calls, validation, and human approval before each catalogue commit. The flow is mostly linear, one item after another, with an agentic tool loop inside each item.

We also call four model providers (OpenRouter, Gemini, Anthropic and Meta's API; the Meta Llama API closed on 6 July 2026, decision 52), which all need tool calling and structured output.

## Options considered

| Option | What it means | Pros | Cons |
|---|---|---|---|
| A. LangChain `create_agent` | The framework runs the whole loop | Least code | The loop, checkpoints and limits are hidden in the framework; the graded part is not our work; a baseline would be a different loop |
| B. LangGraph | Graph with built-in checkpointer and interrupts | Mature checkpointing and HITL | The core of Case 5 is done by the framework; graph features are unused for a linear queue; learning curve and hidden behaviour |
| C. Mix: LangGraph loop + our approvals and limits | Split ownership of the loop | Less checkpoint code | Two mental models; unclear what to debug; the baseline comparison is not like for like |
| D. Fully hand-built, including provider adapters | Everything ours | Full control | Re-implements routine provider and tool-schema plumbing for four providers |
| **E. Custom harness on LangChain plumbing** | **Our loop and control logic; LangChain for chat models, tool schemas and structured output** | **Graded parts are ours and inspectable; routine plumbing is from a tested framework; clean baseline switch** | LangChain version churn; some provider-specific settings need our own wrapper |
| F. Other frameworks (PydanticAI, CrewAI, Google ADK, Microsoft Agent Framework) | A different agent framework | Some offer typed tools | Same objection as A/B (they own the loop); no advantage for our linear queue |

## Decision

**Option E.**

- **Ours:**
  - the code-driven durable work queue
  - the model-driven tool-calling loop per item
  - checkpoints after every tool result, with resume from a compact context
  - idempotency keys for side-effect tools
  - the tool allow-list and Pydantic argument validation
  - the approval queue
  - limits on steps, time, EUR cost and retries
  - retry and backoff policy
  - trace hooks to Langfuse and Postgres
  - the **baseline switch** (same code with checkpoints, queue persistence and durable approvals turned off)
- **LangChain:**
  - chat models for the four providers, behind our thin `ModelClient` wrapper
  - `bind_tools` from our Pydantic argument models
  - `with_structured_output`
  - the `TypeSafeClassifier` runnable for the decision layer
- **Not used:** LangChain agent APIs (`create_agent`, AgentExecutor) and LangGraph.

## Reasons

1. **The brief grades the harness.** Checkpoints, resume, approvals and limits must be our own code to be evidence of our own engineering.
2. **A fair experiment (E4).** The baseline is the same code with one config switch, so differences in completion, cost and recovery come from checkpointing alone.
3. **Fit to the workflow.** A linear item queue does not need graph orchestration or multi-agent features.
4. **No reinvention where it adds nothing.** Provider adapters, tool-schema conversion and structured output are routine, well-tested framework work.

## Consequences

- More of our own code to test: unit tests for the loop, checkpoint and resume, idempotency, limits and the approval state machine; failure-injection tests for E4.
- LangChain packages are **pinned**. A contract test per provider catches breakage on upgrade.
- **Built in MKC-13 (decision 52):** `langchain-core` plus the four provider packages, never the `langchain` meta-package (it depends on LangGraph), so `init_chat_model` is not used; a provider factory builds the chat models. An ast-based guard test keeps agent APIs, LangGraph and direct provider imports out of the code.
- Our `ModelClient` wrapper adds what the abstraction hides: OpenRouter zero-data-retention routing parameters, EUR cost per call, timeouts and trace hooks.
- **Mapping to LangChain concepts** (for the review): our tool registry maps to tools / `@tool`, our harness hooks to middleware, our checkpoint store to a checkpointer, our approval queue to HITL interrupts, and our run state to agent state.
- **Optional extra (Phase 8):** port the extraction run to LangGraph as a third arm in E4, to compare the approaches with data.
